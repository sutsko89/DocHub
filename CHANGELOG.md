## 2.17.0 — 2026-11-20 (окно: нативное перетаскивание на второй монитор и Aero Snap)

Критический отзыв пользователя: окно нельзя было перетащить на второй
монитор, не работал Snap (разворачивание перетаскиванием к краям).

### Причина
* Окно безрамочное (`win_shell.make_borderless` → `overrideredirect`),
  перенос делался вручную через `geometry()` с зажимами `x ≥ −40`,
  `y ≥ 0` — на монитор слева/сверху окно утащить было невозможно в
  принципе, а Windows при ручном переносе не видит «перетаскивание за
  заголовок»: Aero Snap недоступен. Ручное растягивание за кромки к тому
  же зажималось рабочей областью основного монитора (`workarea()` без
  аргумента).

### Исправление
* `win_shell.begin_native_move` / `begin_native_resize` (2.17.0):
  перенос и растягивание отдаются самой Windows через синтетический
  `WM_NCLBUTTONDOWN` с HT-кодом точки (HTCAPTION / HT* восьми кромок).
  Windows ведёт нативный модальный цикл: окно уносится на второй монитор
  (со штатной обработкой смены DPI через `WM_DPICHANGED`), работает
  Aero Snap прилипанием к краям и верхней кромке.
* `make_borderless` добавляет окну стилевые биты WS_MAXIMIZEBOX /
  WS_MINIMIZEBOX / WS_SYSMENU (визуального следа нет) + SetWindowPos
  FRAMECHANGED: без них Snap считает окно неразворачиваемым.
* `ui.WindowDrag._press`: сначала нативный перенос, ручной путь сохранён
  как fallback (не-Windows, сбой Win32-вызова). Поведение «тянешь
  развёрнутое окно — восстанавливается под курсором» сохранено
  (`on_start` срабатывает до запуска нативного цикла).
* Растягивание за 8 кромок (`main._resize_press`): нативный цикл вместо
  ручного; fallback учитывает рабочую область того монитора, где окно
  (`workarea(self.root)`).
* Тесты: HT-мапа всех восьми кромок и системные константы; не-Windows
  ветки `begin_native_move`/`begin_native_resize` возвращают False
  (фейковое окно, `skipif(win32)`).

Проверено: pytest — 510 тестов под Xvfb (0 failures), smoke_test —
322 проверки.

## 2.16.0 — 2026-11-20 (отзыв на проверку релиза: подпись кода в CI, чистые обновления установщика)

Ответ на проверку релиза v2.15.0 на реальном ПК: предупреждение
SmartScreen «неизвестный издатель» и требования к чистоте первой
установки / сохранности данных при обновлении.

### Подпись кода (SmartScreen «неизвестный издатель»)
* Релизный workflow научился подписывать артефакты: при заданных секретах
  репозитория `SIGN_CERT_PFX` (base64 .pfx) и `SIGN_CERT_PASSWORD` шаги
  `tools/sign_artifact.ps1` подписывают `EW.DocHub.exe` и setup.exe
  (signtool, SHA-256, RFC-3161 таймштамп) и проверяют подпись; SHA-256
  релиза считается по уже подписанному файлу. Секретов нет — шаги
  пропускаются, сборка остаётся рабочей.
* README: новый раздел «Подпись кода» — почему появляется предупреждение,
  варианты сертификатов (Certum Open Source, OV/EV, Azure Trusted
  Signing) и включение подписи двумя секретами, без правок кода.
* Шапка `installer.iss` описывает оба пути подписи: автоматический (CI)
  и ручной (SignTool «EWSign»; строки в [Setup] по-прежнему
  закомментированы).

### Чистые обновления установщика
* `installer.iss`: новая секция [InstallDelete] — перед копированием
  новых файлов {app} очищается от файлов прошлой версии (устаревшие
  библиотеки PyInstaller не накапливаются). Профиль пользователя
  (%APPDATA%\DogovorGenerator) не затрагивается.
* README «Установка и обновление»: зафиксировано поведение первой
  установки и обновления; добавлен способ сброса к «первой установке»
  (удаление %APPDATA%\DogovorGenerator при закрытой программе).

### Контракт данных — автотесты
* Новый `tests/test_first_install_state.py` (5 тестов): свежий профиль —
  пустой реестр (контрагенты, документы, корзина), файла ключа DaData
  нет (включая legacy-каталог DogovorPostavki), settings.json не
  создаётся до первого сохранения настроек, из файлов профиля появляется
  только database.db; обновление поверх — реестр, настройки и ключ
  переживают «переустановку».
* Требования пользователя закреплены регрессионным барьером: «при первой
  установке реестр чист и ключа нет», «при обновлении данные остаются».

### Прочее
* `tools/sign_artifact.ps1` — новый скрипт подписи для CI (Windows).
* README: счётчики тестов актуализированы (506 pytest, 322 smoke).

Проверено: pytest — 506 тестов (490 passed + 16 skipped без дисплея),
smoke_test — 322 проверки под Xvfb.

### Исправлен Windows-CI (падал с 2.14.0, блокировал сборку релиза)
* **Пять тестов `test_win_shell.py`** закрепляют не-Windows ветки
  (фейковые окна, fallback-путь «Документов»), но на Windows-раннере
  функции идут по ветке реального Win32 — фейк на неё не действует:
  `documents_known_folder` возвращал реальный `C:\Users\…\Documents`
  вместо подменённого, `workarea` — реальный монитор 1024×720 вместо
  фейковых 1366×768. Тесты помечены `skipif(win32)`; поведение самих
  функций на Windows покрыто smoke-тестом реального приложения.
* **`storage._quarantine_corrupt_db`: retry и fallback при замене
  повреждённой базы.** На Windows `os.replace` только что записанного
  файла падает с PermissionError/WinError 32 — файл на несколько секунд
  блокируется антивирусным сканом (Defender). Замена ретраится 10 раз с
  растущей паузой (~2,75 с суммарно), затем — fallback: содержимое
  копируется в `.bad-копию` (чтение не требует эксклюзивной блокировки),
  оригинал удаляется; конкретная ошибка логируется. Касается реальных
  пользователей Windows, не только CI: `.bad-копия` больше не теряется
  из-за гонки со сканером.
* **`storage._load`: ретраи чтения при временной блокировке.** На
  Windows свежесозданный файл базы может несколько секунд быть
  заблокирован антивирусным сканом — `sqlite3.connect` падает с
  OperationalError «unable to open database file» / «locked», и
  приложение получало пустой реестр вместо миграции. Чтение ретраится
  5 раз с растущей паузой (~2,5 с суммарно); не-временные ошибки идут
  прежним маршрутом (quarantine/предупреждение).
* **smoke_test.py форсирует UTF-8 вывод** (`sys.stdout.reconfigure`):
  Windows-раннер CI запускает smoke в консоли cp1252, где кириллицы нет —
  первый же `print("ok: …")` падал с UnicodeEncodeError. Дублируется
  `PYTHONIOENCODING: utf-8` в шагах smoke обоих workflows.
* Smoke устойчивее к FS-гонкам Windows-раннера: удаление свежесозданной
  базы ретраится; DPAPI-чек отделяет «среду без рабочего DPAPI» от
  ошибки кода пробой `_dpapi_protect` (в среде без DPAPI ключ
  сохраняется открытым текстом — graceful degradation сохранения ключа).
  Блок «сбой записи реестра» использует отдельный APPDATA, где путь базы
  заранее занят каталогом (без манипуляций со свежесозданным файлом);
  миграция JSON → база повторяется с паузами, при неудачных попытках в
  CI-лог печатается diag с load_warning — точная причина видна в сборке.

### Релиз-инфраструктура
* **`.github/workflows/release.yml` публикует GitHub Release** (раньше
  только собирал артефакты): на пуш тега `v*` сборка на windows-latest
  (pytest → smoke → PyInstaller → Inno Setup → SHA-256) выкладывает
  `EW.DocHub-<версия>-setup.exe` и `SHA256SUMS.txt` в Release встроенным
  GITHUB_TOKEN (`permissions: contents: write`,
  softprops/action-gh-release@v2). Установщик не подписан сертификатом —
  SmartScreen покажет предупреждение до появления OV/EV-сертификата.
* **Сборка установщика в CI выполняется впервые** (pytest/smoke раньше
  падали раньше неё) — два соответствующих дефекта исправлены:
  `EWDochub.spec` использует официальный глобал `SPECPATH` вместо
  `__file__` (PyInstaller 6.22 исполняет spec через exec без `__file__`),
  а комментарии секции `[Code]` в `installer.iss` заменены с `;` на `//`
  (`;` не является комментарием Pascal-скрипта — «'BEGIN' expected»).


## 2.14.0 — 2026-11-19 (P3: единый путь расчёта сумм/НДС — этап 9 завершён)

Последний незакрытый пункт этапа 9 — п. 9.8: предпросмотр, реестр и
печатная форма считают суммы спецификации одним расчётом. Пункты 9.5
(дубли/мусор) и 9.7 (константы в settings.json) верифицированы как
закрытые в предыдущих релизах — этап 9 завершён целиком.

### Единый путь расчёта сумм/НДС (п. 9.8)
* **Новая семантика итога.** `document_builder.spec_line_total(item)` —
  сумма позиции с копеечным округлением (ROUND_HALF_UP);
  `spec_total(items)` — итог как сумма уже округлённых строк («как в 1С»).
  Раньше «Итого» считался сырой суммой qty × price в четырёх местах
  (SpecTable.total, DocumentSaveController.spec_total, предпросмотр,
  save_spec → extra → печатная форма) и мог расходиться с таблицей
  на копейку: 3 × 3,335 + 1 × 1,115 — строки дают 11,13, сырая сумма
  11,12, печатная форма показывала в «Итого» 11,12 при строках 10,01 + 1,12.
* **Все потребители переведены:** предпросмотр спецификации (строки и
  итог через spec_line_total/spec_total), сохранение в реестр
  (extra["total"] — сумма строк), печатная форма (services.render_spec —
  итог всегда из позиций: старые записи с сырым total в extra печатаются
  по исправленному итогу; без позиций — как записано). НДС по позициям
  (spec_vat_amount_from_items) использует тот же spec_line_total —
  НДС, итог и строки согласованы между собой.
* **Дубль удалён (п. 9.5):** мёртвый `SpecTable.total()` (вызовов не было)
  убран; `DocumentSaveController.spec_total()` делегирует общему расчёту.
  Из импортов ушли ставшие лишними ROUND_HALF_UP (save_controller) и
  Decimal (services).
* Поведение golden-образцов не изменилось: в эталонных позициях цены
  целокопеечные, итог совпадает с прежним (450 тестов зелёные).

### Верификация закрытых пунктов этапа 9
* **п. 9.5 (дубли/мусор):** `digits_only` и `_pick_ooo_name` определены
  единожды (document_builder / document_importer); копий

### Тесты

## 2.13.0 — 2026-11-19 (P3: миграция «Покупь» + DPI по п. 6.3)

Два пункта этапов 6/9 плана: исправлена опечатка в имени поля
«Полное название компании (Покупь)» (единый источник имён полей —

при переносе между экранами с разным масштабом.

### Миграция поля «Покупь» → «Покупатель»
* **Ключ поля — из константы.** `F.FULL_NAME` =
  «Полное название компании (Покупатель)»; `storage.py` больше не держит
  копии строки: `find_by_name` и `display_name` импортируют `F`
  (п. 9.6 — единый источник имён полей; цикла импорта нет —
  `document_builder` не зависит от `storage`).
* **Миграция при загрузке.** `storage._normalize_field_names` переименовывает
  старый ключ в `fields` карточек контрагентов **и** в `data` сохранённых
  документов (копия полей карточки на момент сохранения — иначе печатная
  форма старого договора теряла название). Применяется в `_read_all`,
  при переносе legacy-JSON и в `add_counterparty`/`update_counterparty`
  (защита старых callers). Идемпотентно; при обоих ключах остаётся новое
  значение, старое отбрасывается.

## 2.11.0 — 2026-11-19 (SQLite вместо JSON)

Пункт 11 этапа 5 плана — источник правды реестра переведён с JSON-файла
на SQLite-базу (`database.db`). API `DataStore` не изменился ни на один
метод: в памяти — те же два списка словарей, все контроллеры, тесты и
smoke-подмены работают как раньше. Полный pytest 417 → 422 зелёный.

### Архитектура
* **База `database.db` вместо `database.json`** (storage.py переписан,
  публичный API и поведение методов сохранены 1-в-1):
  - WAL-журнал (`PRAGMA journal_mode=WAL`) — чтение не блокирует запись,
    второй экземпляр программы безопасно работает параллельно;
    `busy_timeout=5 c` вместо мгновенного сбоя при занятой базе.
  - `synchronous=FULL` — коммит доходит до диска до подтверждения
    (замена fsync у старых `.bak`-копий, гарантия сбоя питания).
  - Запись — одна транзакция на весь реестр: либо всё, либо ничего;
    при сбое предыдущая версия базы не теряется, `last_error` заполняется
    как раньше (до 3 попыток при временных сбоях — антивирус, индексатор).
  - Сериализация до открытия базы: битые данные не роняют файл.
* **Индексы.** `counterparties.inn` — отдельная колонка с индексом
  `idx_counterparties_inn` (поиск по ИНН из DaData-поиска); индексы
  документов по контрагенту и типу (`idx_documents_party`,
  `idx_documents_kind`) и по корзине (`idx_*_deleted`).
* **Миграция JSON → SQLite.** При первом запуске пустая база читает старый
  `database.json` (те же проверки структуры, что раньше) и переносит записи;
  перенесённый файл сохраняется как `database.json.migrated`. Повторный
  перенос невозможен (триггер — пустая база без метки `meta.seq`). Битый
  legacy-JSON не трогается — это единственная копия данных, пользователь
  предупреждается. Дубли id при переносе схлопываются (база не допустит
  второй записи с тем же PRIMARY KEY), счётчик id продолжается.
* **Схема без потерь.** Ключи записи, у которых нет собственной колонки
  (запас на будущее), сохраняются в `extra_keys` как JSON и восстанавливаются
  при чтении — перенос в обе стороны не теряет ни одного ключа.
* **Повреждённая база** (не SQLite-файл / «disk image is malformed») —
  убирается в `database.db.bad-<метка>` (вместе с `-wal`/`-shm`), реестр
  начинается с пустой базы, предупреждение показывается как раньше; старые
  `.bad`-копии (включая `database.json.bad-*` прежних версий) чистятся
  по возрасту, как и было (аудит 2.0.1).
* **Ушло с JSON-бэкендом:** ротация `.bak.1…4`, черновики
  `database.json.<pid>.tmp`, восстановление из `.tmp` — их роль взяли на
  себя транзакции и WAL.

### Архитектура (этап 9)
* `document_builder.py` — печатные формы (F, PH, замены, НДС) вынесены
  из main.py (п. 9.1).
* `services.py` — сервисный слой: валидация, кэш шаблонов, запись .docx,
  транзакция «файл → запись реестра» с откатом (п. 9.2); UI только
  собирает данные и показывает результат.
* `win_shell.py` — Win32-обвязка окна (п. 9.3); `widgets.py` — SpecTable
  (п. 9.4); `document_importer.py` использует единый источник имён полей
  F (п. 9.6); константы печатной формы спецификации (поставщик, город,
  год, ставка НДС, номер приложения) — в settings.json (п. 9.7).
* Расчёт НДС — единый для предпросмотра и печатной формы (п. 9.8).
