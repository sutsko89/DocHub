## Вердикт

**Функциональные требования в целом понятны** — назначение программы документировано
в [`README.md`](README.md) и подтверждается структурой кода. **Но формального
документа требований нет**: спецификация «рассыпана» по README, докстрингам и коду,
а критерии «правильного результата» определены только частично (для чистой логики
есть smoke-тест, для сценария импорта — лишь эвристики без эталона).

## 2. Пользовательские сценарии (7 основных)

1. **Первый запуск без контрагентов** → по README ([README.md:99](README.md:99))
   автоматически открывается окно добавления; **фактически** открывается страница
   «Договор поставки» с пустым списком (см. раздел 11.3).
2. **Создание контрагента** → ручной ввод или DaData по ИНН → сохранение в реестр.
3. **Генерация договора** → выбор контрагента, номер/дата → `.docx` в папке
   контрагента → автозапуск Word.
4. **Генерация доп. соглашения** (привязка к существующему договору: лимит, отсрочка).
5. **Генерация спецификации** → таблица позиций (в т.ч. вставка из Excel) → суммы и НДС.
6. **Импорт готовых документов** → фоновый анализ → распределение по папкам
   контрагентов / `unknown`.
7. **Реестр** → просмотр, открытие, удаление документов; удаление контрагента
   каскадно удаляет его документы.

## 3. Что в требованиях НЕясно / не формализовано (пробелы)

1. **Импорт документов — нет эталона «правильного распознавания».**
   [`detect_kind()`](document_importer.py:121) — эвристика по заголовку и частоте
   слов; не определено: что считать допустимой ошибкой распознавания, как трактовать
   неоднозначные документы (договор со спецификацией внутри, акт, счёт).
2. **Дубликаты контрагентов.** Нигде не задано: можно ли иметь двух контрагентов
   с одинаковым ИНН? [`find_by_inn`](storage.py) вернёт первый найденный —
   поведение при дубликатах не определено.
3. **Дубликаты документов при импорте.** Не определено, что делать при повторной
   загрузке того же файла или документа с тем же номером.
4. **Хардкод НДС.** Ставка задаётся константой `SPEC_VAT_RATE`
   ([main.py:272](main.py:272)) — неясно, должно ли быть редактируемым в UI
   (ставки НДС меняются).
5. **Отказоустойчивость DaData.** Описана ошибка запроса
   ([dadata_client.py:35](dadata_client.py:35)), но нет требований: что делать при
   недоступности сервиса (только ручной ввод? повтор?) и о сроке действия вшитых
   API-ключей ([dadata_client.py:25](dadata_client.py:25) — ключи в исходнике,
   вопрос безопасности).
6. **Удаление контрагента каскадно удаляет документы**
   ([`_delete_counterparty()`](main.py:3294)) — является ли это требованием бизнеса
   или риском потери данных (нет подтверждения с перечнем, нет корзины)? README
   фиксирует поведение, но не обосновывает.
7. **Правка контрагента не влияет на старые документы** (README:15) — требование
   зафиксировано явно, это хорошо; но не описано, как исправить ошибку в уже
   выпущенном документе (пересоздать? редактировать текст в Word?).
8. **Мультиплатформенность.** Код использует `%APPDATA%` и Win32
   ([`toggle_zoom()`](main.py:1713)), есть [`ui_macos.py`](ui_macos.py) — целевые ОС
   явно не сформулированы (де-факто Windows-only).

## 4. Где «правильный результат» определён, а где нет

**Определено (можно проверить автоматически)** — [`smoke_test.py`](smoke_test.py),
~330 строк: маска телефона ([smoke_test.py:40](smoke_test.py:40)), числа/суммы
прописью, валидаторы, хранилище, шаблоны. Это хороший, но узкий критерий.

**Не определено (принято на веру):**

- **Точное соответствие печатной формы образцам** — эталонные `.docx` лежат в
  [`образцы/`](образцы/) и в корне проекта («Договор поставки №516…»,
  «Спецификация №12…»), но нет автоматического сравнения результата генерации
  с образцом. Критерий «документ выглядит как образец» существует только
  в голове разработчика.
- **Правильность НДС/итогов спецификации** — логика «как в 1С»
  ([main.py:280](main.py:280)) без тест-кейсов.
- **Правильность распознавания импорта** — нет набора тестовых файлов
  с ожидаемым результатом.
- **Полный пользовательский сценарий** — smoke-тест подменяет UI
  ([smoke_test.py:25](smoke_test.py:25)), реальное прохождение «создать контрагента →
  договор → спецификация» автотестом не покрывается.

## 5. Функциональный анализ: правильно ли реализованы нужные возможности?

Методы проверки: изучение кода генерации; сверка всех плейсхолдеров шаблонов
`.docx` с классом `PH` (скриптом); прогон [`smoke_test.py`](smoke_test.py:1);
функциональная сборка всех шести печатных форм (ООО/ИП) с поиском
незаменённых плейсхолдеров; прогон импорта на 5 реальных образцах.

### 5.1. Сверка шаблонов и кода

В пяти шаблонах суммарно 93 уникальных плейсхолдера. Сверка с классом `PH`
([main.py:202](main.py:202)) и словарями замен из [`build_replacements()`](main.py:865)
показала: **все токены шаблонов имеют соответствие в коде** (лишние замены
в коде, которых нет в шаблоне, безвредны — например, `{{limit_in_words}}`
отсутствует в шаблонах доп. соглашений).

### 5.2. Результаты функциональной сборки документов

| Документ | Результат |
|---|---|
| Договор ООО (`dogovor_template.docx`) | OK — все плейсхолдеры заменены |
| Договор ИП (`dogovor_template_ip.docx`) | OK — все плейсхолдеры заменены |
| Доп. соглашение ООО (`additional_agreement.docx`) | OK — все плейсхолдеры заменены |
| Доп. соглашение ИП (`additional_agreement_ip.docx`) | OK — все плейсхолдеры заменены |
| Спецификация ООО (`spec_template.docx`) | OK — все плейсхолдеры заменены |
| **Спецификация ИП** | **БАГ — остаются незаменёнными `{{KPP}}` и `{{OGRN}}`** |

**Подтверждённый баг: спецификация для ИП.** IP-ветка
[`build_replacements()`](main.py:869) не содержит `PH.KPP` и `PH.OGRN`
(у ИП этих кодов нет), а шаблон спецификации написан «в терминах ООО» и
содержит `{{KPP}}`/`{{OGRN}}`. Переопределение для ИП в
[`_render_spec_docx()`](main.py:2881) подставляет только name-поля
(`FULL_NAME`, `SHORT_NAME`, `DIRECTOR`, `DIRECTOR_INITIALS`, `BASIS`), но
не трогает KPP/OGRN. В итоге печатная форма спецификации для ИП содержит
литеральные `{{KPP}}` и `{{OGRN}}`. Исправление — 2 строки: в ветке `is_ip`
в `_render_spec_docx` добавить `replacements[PH.KPP] = ""` и
`replacements[PH.OGRN] = ""` (либо текст-заглушку).

### 5.3. Корректность остальной механики генерации

- **Замена плейсхолдеров** ([`replace_in_paragraph()`](main.py:700)) корректно
  работает с плейсхолдерами, разбитыми на runs (Word часто так делает),
  в таблицах и колонтитулах. Риски (на текущих шаблонах не проявляются):
  не обрабатываются runs внутри гиперссылок (`w:hyperlink`), колонтитулы
  первой/чётной страниц (`first_page_header`/`even_page_header`), а
  [`fill_spec_items()`](main.py:795) заменяет токен только если он целиком
  внутри одного run — при разбивке `{{item_*}}` на runs замена пропадёт.
- **Суммы и НДС**: итог — сумма позиций; НДС «в том числе» считается по
  каждой позиции (`сумма × 22 / 122`, `ROUND_HALF_UP`) как в 1С
  ([`spec_vat_amount_from_items()`](main.py:280)) — корректно; итоговый
  блок начинается с новой страницы ([`mark_spec_final_page()`](main.py:838)).
- **Форматирование**: разряды, копейки при наличии дробной части, количество
  без дробной части для целых — покрыто smoke-тестом, работает.
- **Сохранение/экспорт**: файл кладётся в индивидуальную папку контрагента,
  конфликт имён решается суффиксами «(2)», «(3)»
  ([`_save_and_open_document()`](main.py:2963)); при экспорте из реестра
  документ всегда **перегенерируется из шаблона**
  ([`export_document()`](main.py:3251)) — правки пользователя, внесённые
  в файл в Word, при повторном открытии из реестра теряются.
- **Несоответствие README**: поле «Текст документа — можно редактировать»
  сохраняется в `rec["text"]`, но при сборке `.docx` игнорируется — ручные
  правки текста предпросмотра никогда не попадают в печатную форму.
- **Дублирование**: [`validate_additional_agreement_required()`](main.py:392)
  не используется — валидация лимита/отсрочки продублирована вручную в
  [`save_additional()`](main.py:3121).
- **Хардкоды**: ставка НДС 22% ([main.py:269](main.py:269)), поставщик
  «ООО «Эдельвейс»», город «г. Хабаровск», год «2026» в текстовом
  предпросмотре ([main.py:2998](main.py:2998)–[main.py:3002](main.py:3002)) —
  стоит вынести в настройки.

### 5.4. Импорт документов ([`document_importer.py`](document_importer.py:1)) — прогон на 5 образцах

| Файл | Тип | Номер/дата | Контрагент |
|---|---|---|---|
| Договор поставки ООО «ЛИДЕР ДВ».docx | OK contract | OK | OK: ИНН/КПП/ОГРН распознаны |
| Договор поставки №516 ООО ЛИДЕР ДВ.docx | OK contract | OK | OK: ИНН/КПП/ОГРН распознаны |
| Доп. соглашение ООО «ЛИДЕР ДВ».docx | OK additional | OK | см. пункт 1 ниже |
| Спецификация Эдельвейс (1).xlsx | OK spec | OK | OK: ИНН/КПП/ОГРН распознаны |
| Спецификация №12 ООО ЛИДЕР ДВ.docx | OK spec | дата не найдена | КПП/ОГРН пустые |

**Типы документов распознаются верно на всех образцах** — главная задача
импорта работает. Но качество извлечения реквизитов неравномерное:

1. В доп. соглашении в название попал мусор:
   `ООО "ЛИДЕР ДВ", именуемый в дальнейшем`; ИНН/КПП/ОГРН не распознаны →
   будет создана карточка с неполными реквизитами (а без ИНН не сработает
   привязка к уже существующему контрагенту).
2. Расчётный счёт не распознан **ни в одном** образце (шаблон `_ACCOUNT_RE`,
   [document_importer.py:158](document_importer.py:158), не совпадает с
   написаниями «Р/счёт» в реальных документах).
3. `recognized=true` возвращается даже при пустых ключевых реквизитах →
   создаются «полукопии» контрагентов вместо привязки к существующим.
4. Dead code: функция `_pick_ooo_name` определена дважды
   ([document_importer.py:262](document_importer.py:262) и
   [document_importer.py:322](document_importer.py:322)) — первое
   определение перекрыто вторым.

## 6. Архитектурный анализ: как устроена программа и насколько удобно её развивать?

### 6.1. Текущая структура модулей

| Модуль | Строк | Слой | Чистота (отсутствие зависимостей от UI) |
|---|---|---|---|
| [`main.py`](main.py:1) | ~4260 | смешанный | ❌ половина — чистая логика, половина — UI |
| [`ui_macos.py`](ui_macos.py:1) | ~1940 | UI | — (виджеты, палитра, алерты) |
| [`storage.py`](storage.py:47) | ~240 | данные | ✅ без UI |
| [`document_importer.py`](document_importer.py:1) | ~520 | бизнес | ✅ без UI, чистые функции |
| [`dadata_client.py`](dadata_client.py:1) | ~130 | внешние API | ✅ только stdlib |

### 6.2. Что разделено хорошо

- **Хранение данных** — [`storage.py`](storage.py:47): пассивный `DataStore`
  (JSON в `%APPDATA%`), никак не связан с UI, атомарная запись, самовосстановление
  счётчика ID. Разделение соблюдено.
- **Импорт документов** — [`document_importer.py`](document_importer.py:1):
  чистые функции (`extract_text` → `detect_kind` → реквизиты), тестируется
  без UI; фоновый поток и очередь — уже в [`main.py`](main.py:3709)
  (оркестрация, что допустимо).
- **Внешний API** — [`dadata_client.py`](dadata_client.py:1) изолирован,
  не тянет UI-зависимостей.
- **Стилистика интерфейса** — [`ui_macos.py`](ui_macos.py:1): палитра,
  карточки, «светофор», алерты в одном месте; [`main.py`](main.py:40) не
  рисует ничего напрямую.
- **Единый источник имён** — классы [`F`](main.py:172) и [`PH`](main.py:202):
  ключи полей и плейсхолдеры не дублируются; smoke-тест дополнительно
  проверяет синхронность ключей импортёра и карточки.
- **Тестируемая «голова»** — все форматтеры, валидаторы и DOCX-движок
  ([`replace_in_paragraph()`](main.py:700), [`fill_spec_items()`](main.py:795),
  [`build_replacements()`](main.py:865)) — чистые функции, покрытые
  [`smoke_test.py`](smoke_test.py:1).

### 6.3. Что разделено плохо

1. **[`main.py`](main.py:1) — монолит на ~4260 строк**, в котором живут:
   валидация и форматирование (строки 97–860), DOCX-движок (699–919),
   UI-виджет [`SpecTable`](main.py:1013) (Excel-таблица позиций — по смыслу
   должен быть в `ui_macos.py`), god-object [`ContractApp`](main.py:1542)
   (~2700 строк: шесть страниц UI, сценарии сохранения, поток импорта,
   предпросмотр, Win32-манипуляции окном через `ctypes`, настройки).
2. **Нет сервисного слоя.** Сценарии ([`save_contract()`](main.py:3050),
   [`save_additional()`](main.py:3102), [`save_spec()`](main.py:3169))
   смешивают бизнес-логику (валидация, сборка записи) с UI (алерты,
   подсветка ошибок, refresh реестра) в одном методе — переиспользовать
   логику или тестировать её без GUI нельзя.
3. **Генерация документов не выделена.** Чистые функции DOCX-движка соседствуют
   с методами UI-класса [`_render_*_docx()`](main.py:2848) — вынос в
   отдельный модуль напрашивается, но пока границы размыты.
4. **Интерфейс и данные связаны косвенно, но тесно**: `ContractApp` напрямую
   мутирует `store` и сам вызывает `refresh_registry()` из ~20 мест;
   нет событий/наблюдателей — рассинхронизация страниц при изменениях
   обрабатывается вручную (например, [`_delete_document()`](main.py:3287)
   обязан помнить про предпросмотры двух страниц).
5. **Тестируемость через monkey-patching**: [`smoke_test.py`](smoke_test.py:25)
   подменяет `m.ui.alert` и `m.open_file` — признак, что зависимости не
   инвертированы, а «зашиты» в код приложения.

### 6.4. Насколько удобно развивать

**Плюсы для развития**: небольшая кодовая база (~9000 строк), интуитивные
имена, подробные докстринги на русском, единые F/PH, есть smoke-тест,
сборка и установщик автоматизированы ([`EWDochub.spec`](EWDochub.spec),
[`installer.iss`](installer.iss)). Добавить новое поле контрагента —
несложно: F + поле в карточке + плейсхолдер + строка в `build_replacements`.

## 7. Ревью кода: ошибки и сложные для сопровождения участки

Количественные данные собраны AST-анализом по всем модулям.

### 7.1. Ошибки и риски потери данных

1. **Молчаливая потеря реестра при повреждённом `database.json`.**
   [`DataStore._load()`](storage.py:59) при любой ошибке чтения/парсинга
   делает `except Exception: return` — приложение стартует с **пустым**
   реестром, и первый же `save()` перезапишет (возможно ещё пригодный)
   файл. Ни предупреждения, ни резервной копии. Минимум: переименовать
   повреждённый файл в `database.json.bad` и сообщить пользователю.
2. **Результат `save()` нигде не проверяется.** [`save()`](storage.py:82)
   возвращает `bool`, но [`add_counterparty()`](storage.py:111),
   [`update_counterparty()`](storage.py:128), [`add_document()`](storage.py:153)
   и все сценарии UI вызывают его, не глядя на результат: при недоступном
   диске UI покажет «Договор сохранён», а запись в `database.json` не
   произойдёт (файл `.docx` при этом сохранится — реестр и папка
   документов разойдутся).
3. **Подтверждённый функциональный баг** — спецификация для ИП с
   `{{KPP}}`/`{{OGRN}}` в печатной форме (см. раздел 5.2).
4. **`parse_decimal()` возвращает 0 при ошибке** ([main.py:473](main.py:473)):
   вместо исключения — тихий ноль. Валидация UI предотвращает это для ввода,
   но данные импорта и старых записей реестра валидацию не проходят —
   «мусорная» цена молча станет нулевой в печатной форме.
5. **float в JSON для денег** ([`save_spec()`](main.py:3213): `qty`, `price`,
   `total` — float): конверсия Decimal→float→Decimal работает через
   кратчайший `repr` и на практике корректна, но это хрупкое место —
   для денег в JSON лучше строки.
6. **Секреты в исходнике** — API-ключи DaData вшиты в
   [`dadata_client.py:25`](dadata_client.py:25): любой, кто получит
   `.exe`/репозиторий, получит ключ и лимиты вашей учётной записи.

## 8. Анализ данных и хранения: сохраняются ли данные корректно и согласованно?

### 8.1. Как устроено хранение

- Реестр: `%APPDATA%/DogovorGenerator/database.json`
  ([`storage.py:43`](storage.py:43)) — контрагенты + документы в одном файле.
  Запись **атомарная**: сначала в `database.json.tmp`, затем
  [`os.replace()`](storage.py:98).
- Настройки: `settings.json` ([main.py:70](main.py:70)); ключ DaData — в
  **другой** папке `%APPDATA%/DogovorPostavki`
  ([dadata_client.py:42](dadata_client.py:42)).
- Печатные формы — `.docx` в `<папка документов>/<контрагент>/`.

**Снимки реквизитов — осознанное и правильное решение**: каждый документ
хранит копию `data` на момент создания ([storage.py:169](storage.py:169)),
поэтому правка карточки не искажает выпущенные документы, а экспорт всегда
перегенерирует документ из записи (`export_document` → `_build_record_docx`)
— документы воспроизводимы, «файл как источник истины» не нужен.

### 8.2. Целостность JSON

- Атомарная запись — да (tmp + os.replace на том же томе).
- **Чтение — нет защиты**: [`_load()`](storage.py:59) при повреждённом файле
  молча стартует с пустым реестром, и первый `save()` перезапишет файл
  (подробно — раздел 7.1, п. 1). Нет версии схемы, нет резервной копии,
  нет валидации структуры записей (только `isinstance(rec, dict)`).

### 8.3. Согласованность «реестр ↔ файлы на диске» — главный слабый узел

Порядок операций при [`save_contract()`](main.py:3050):

1. `store.add_document(...)` → запись в **памяти** + `save()`
   (результат `save()` игнорируется);
2. `refresh_registry()` — запись уже видна в UI;
3. `_save_and_open_document()` — только теперь создаётся `.docx`.

Разбор сценариев сбоя:

| Сценарий | Что происходит | Последствие |
|---|---|---|
| **`save()` не удался, `.docx` создался** (ответ на вопрос) | запись живёт только в памяти; после перезапуска приложения исчезает | **«Осиротевший» `.docx` остаётся в папке контрагента навсегда** — папку программа никогда не сканирует, файл не попадёт в реестр; при повторном создании того же договора появится дубль «Договор №N … (2).docx» |
| Запись в JSON удалась, `.docx` создать не удалось | запись есть, файла нет; пользователю показан алерт об ошибке | **Самовосстановление**: клик по документу в реестре перегенерирует `.docx` из записи |
| Исключение между шагами 1 и 3 | запись добавлена в память, показан алерт | до перезапуска запись работает; после перезапуска зависит от того, удался ли `save()` |

**Итог по сценарию «файл создан, запись не сохранилась»**: прямого вреда
нет (сам файл корректен и открывается), но реестр — единственный источник
правды — начинает врать: документ существует на диске, но не виден в
программе. Механизма сверки/очистки нет.

**Импорт — тот же паттерн наоборот**: файл сначала копируется в папку
контрагента ([`_import_worker()`](main.py:3709) →
[`_copy_imported_file()`](main.py:3726)), и только потом регистрируется
([`_finish_documents_import()`](main.py:3783)). Сбой регистрации оставляет
файл-сироту в папке контрагента или `unknown`. При этом **и обычные документы,
и раздел «Неопознанные документы» строятся только по записям реестра**:
[`_render_registry_unknown()`](main.py:2644) фильтрует `store.documents`, а не
содержимое папки. Папка документов не сканируется нигде, поэтому потеря
`database.json` из файлов автоматически не восстанавливается.

### 8.4. Удаление и переименование: реестр ≠ диск

- [`delete_counterparty()`](storage.py:192) удаляет **записи**, но физические
  файлы и папку контрагента никто не удаляет — на диске остаются `.docx`
  «удалённого» контрагента (README обещает «удалить вместе с его документами»
  — фактически только из реестра).
- [`delete_document()`](storage.py:184) — файл `.docx` остаётся на диске.
- **Переименование контрагента**: папка создаётся по текущему имени
  ([`_party_documents_dir()`](main.py:2832)) — новые документы попадут в
  папку с новым именем, старые останутся в старой; `extra.source_file`
  импортированных документов указывает на старый путь (файл откроется, но
  правило «папка = имя контрагента» молча ломается).

### 8.5. Вывод

- **В пределах одного файла данные хранятся корректно** (атомарно, снимки
  реквизитов, самовосстановление счётчика ID).
- **Согласованность «реестр ↔ папка документов» не гарантируется**: ни один
  из сценариев частичного сбоя (осиротевший файл, запись без файла,
  файлы после удаления/переименования) не обнаруживается и не исправляется.

**Рекомендации:**

1. Проверять результат `save()` и предупреждать при неудаче (до записи
   в UI о «сохранено»).
2. Инвертировать порядок в `save_contract/save_additional/save_spec`:
   сначала успешно собрать и сохранить `.docx`, затем регистрировать запись
   (или откатывать запись при сбое файла).
3. Добавить сверку при старте: сканировать папки контрагентов и предлагать
   «восстановить в реестр» / удалить осиротевшие файлы.
4. При удалении контрагента/документа — удалять и физические файлы
   (с явным подтверждением) либо честно сообщать, что файлы остались.
5. При переименовании контрагента — переносить его папку документов и
   обновлять `extra.source_file`.
6. Ввести версию схемы в `database.json` и резервную копию перед записью
   (хранить 1 предыдущую версию).

### 9.2. Сбой 1: закрытие программы во время сохранения

Важное уточнение: **штатное закрытие окна не может прервать сохранение**.
Tkinter однопоточный — обработчик [`save_contract()`](main.py:3050) выполняется
до конца, а событие `WM_DELETE_WINDOW` обрабатывается уже после него. Реальные
окна уязвимости — принудительное завершение (Диспетчер задач, выключение
питания, BSOD), падение процесса и **закрытие во время импорта**, где копирование
файлов идёт в фоновом потоке.

| Что пишется | Как пишется | Что будет при аварийном завершении | Восстановление |
|---|---|---|---|
| `database.json` | tmp + `os.replace`, **без `fsync`** ([storage.py:86](storage.py:86)–[storage.py:98](storage.py:98)) | обычно остаётся предыдущая версия; при сбое питания содержимое tmp может не дойти до диска → пустой/обрезанный JSON. Оставшийся `.tmp` с более новой версией при старте **игнорируется** и затирается следующим сохранением | да, но вручную: переименовать `.tmp` в `database.json` **до** первого сохранения |
| Сгенерированный `.docx` | python-docx пишет прямо в итоговое имя ([main.py:2977](main.py:2977)–[main.py:2978](main.py:2978)) | обрезанный ZIP под «нормальным» именем; запись в реестре при этом уже сохранена (порядок: сначала запись, потом файл) | да: экспорт из реестра пересоберёт файл. Обрезанный файл останется мусором, а следующее сохранение создаст «(2)» |
| `settings.json` | прямая перезапись, **не атомарно** ([main.py:84](main.py:84)–[main.py:94](main.py:94)) | обрезанный/пустой файл → [`load_settings()`](main.py:75) молча вернёт `{}` → тема, геометрия окна и **папка документов** сбрасываются | нет, только вручную |
| Импортируемый файл | `shutil.copy2` сразу в итоговое имя, в фоновом потоке ([main.py:3746](main.py:3746)) | поток-демон убивается, копия остаётся частичной; регистрация ([`_finish_documents_import()`](main.py:3783)) не выполняется | нет: файл-сирота, папка не сканируется |
| Записи импорта | N полных перезаписей JSON — по одной на запись ([storage.py:153](storage.py:153)) | часть файлов зарегистрирована, часть нет; возможна карточка контрагента без документов | частично: повторный импорт вручную |

Отдельно: «закрыть Word во время сохранения» не применимо — Word открывается
только после полной записи файла ([`_save_and_open_document()`](main.py:2977)).

**Вывод по сбою 1:** потеря последней операции возможна только при аварийном
завершении; встроенного журнала, автосохранения и восстановления нет.

| Тип повреждения | Поведение [`_load()`](storage.py:59) | Что видит пользователь | Восстановление |

### 9.6. Что делать пользователю сейчас (без доработки программы)

1. Если реестр «опустел» — **ничего не сохранять**: сначала скопировать папку
   `%APPDATA%\DogovorGenerator` целиком (каждое сохранение перезаписывает файл).
2. Проверить `database.json.tmp`: если открывается как JSON — переименовать
   в `database.json` (там может быть более новая версия).
3. Свойства папки → «Предыдущие версии» / история файлов / теневые копии Windows.
4. Если JSON утрачен: файлы лежат в `<папка документов>\<контрагент>\`; вернуть
   их в реестр можно через «Добавить документы…» — только ручным выбором файлов
   (папка не сканируется). Восстановятся тип, номер, дата, контрагент;
   **не восстановятся** связи «спецификация → договор», позиции и суммы.
5. Заново выбрать папку документов в настройках — иначе новые файлы уйдут
   в `%APPDATA%\DogovorGenerator\documents`.

### 9.7. Оценка надёжности

- **Защищён по-настоящему только один узел** — атомарная замена `database.json`
  при записи. Всё остальное («проверить результат», «не потерять», «сообщить»)
  реализовано частично или отсутствует.
- **Отсутствует**: проверка результата `save()` в вызывающем коде, резервные
  копии, версия схемы, блокировка второго экземпляра, логирование, атомарная
  запись `.docx`, сверка «реестр ↔ папка документов», корзина/отмена удаления.
- **Классификация восстановимости**: сгенерированные документы — восстановимы
  (реестр → файл); импортированные — только если файлы целы и пользователь
  вручную повторит импорт; **реестр при повреждении штатными средствами
  невосстановим**.
- **Профиль риска** (оценка):

| Риск | Вероятность | Ущерб | Защита сейчас |
|---|---|---|---|
| Уничтожение повреждённого реестра первым `save()` | высокая при любом повреждении | критический | нет |
| Молчаливая потеря всего реестра при недоступной папке | средняя | критический | нет |
| Потеря записей при двух запущенных экземплярах | средняя | высокий | нет |
| Откат/порча JSON при выключении питания | средняя | высокий | частично (atomic replace, без `fsync`) |
| Отказ запуска на «полувалидном» JSON | низкая | высокий | нет |
| Обрезанный `.docx` после аварийного завершения | низкая | низкий (пересоберётся) | частично |
| Файлы-сироты после сбоя импорта | средняя | низкий | нет |

## 10. Анализ безопасности: данные, внешние интеграции, импорт файлов

Проверены: хранение данных на диске, работа с ключом DaData, сетевой обмен,
обработка импортируемых `.docx`/`.xlsx`, попадание реквизитов в сообщения и
возможные логи, а также артефакты поставки. Модель угроз — локальное
однопользовательское приложение без сервера и аутентификации: кража/утеря
носителя, другой локальный пользователь, вредоносный процесс под той же учётной
записью, общая/съёмная папка документов, передача папки проекта или сборки
третьим лицам, вредоносный импортируемый файл, злоупотребление вшитым ключом.

| Ключ присутствует в артефактах сборки | `build/EWDochub/EW.DocHub.exe`, `build/EWDochub/PYZ-00.pyz`, `installer/install.exe` | ключ распространяется с каждым установщиком; открытым текстом в бинарниках не лежит (проверено поиском), но извлекается распаковкой PYZ |

**Оценка: критично.** Это не «секрет в коде» в академическом смысле, а
функционально общий пароль на всех клиентов: компрометация одной копии =
исчерпание квоты и потенциальные расходы у владельца ключа, при этом сменить
ключ у пользователей без обновления программы нельзя. Оба ключа следует считать
скомпрометированными и перевыпустить.

### 10.3. Внешняя интеграция DaData и попадание реквизитов в логи

**Что сделано правильно:**

- только HTTPS, стандартная проверка сертификата (`urllib` + системные CA),
  ключ передаётся в заголовке `Authorization`, а не в URL — не оседает в логах
  прокси и истории ([`fetch_party()`](dadata_client.py:66)–[dadata_client.py:75](dadata_client.py:75));
- в запрос уходит **только ИНН** (`{"query": inn}`) — минимизация данных;
- таймаут 10 с ([`TIMEOUT`](dadata_client.py:20)), ошибки 401/429/сети
  преобразуются в понятные сообщения без ключа ([dadata_client.py:79](dadata_client.py:79)–[dadata_client.py:90](dadata_client.py:90));
- нет телеметрии, автообновления и других внешних вызовов; зависимостей, кроме
  стандартной библиотеки, нет.

**Риски и пробелы:**

1. **Ответ не проверяется на соответствие запросу**: [`_parse()`](dadata_client.py:98)
   не сверяет `data["inn"]` с запрошенным ИНН. При подмене ответа (корпоративный
   MITM-прокси с доверенным сертификатом, компрометация DNS/CA) в карточку и
   договор попадут реквизиты другой организации — это ошибка целостности,
   а не только доступности.
2. **Нет закрепления сертификата (pinning)** и нет предупреждения о
   корпоративном прокси: при MITM видны и ИНН, и токен.
3. **Нет повторов/backoff и ограничения частоты** — при 429 программа просто
   сообщает о лимите; массовое автозаполнение легко исчерпывает квоту.
4. **Нет `User-Agent`** — использование ключа не идентифицируется как
   приложение, что затрудняет разбор инцидентов с квотой.
5. **152-ФЗ**: ИНН индивидуального предпринимателя — персональные данные;
   передача в сторонний сервис не описана ни в README, ни в интерфейсе; нет
   уведомления, основания обработки и политики хранения. Ответ DaData (ФИО
   руководителя, адрес) сохраняется в открытом виде бессрочно.
6. **Логи.** Модуля `logging` в проекте нет вообще, файла журнала нет —
   значит, реквизиты в логи **сейчас не попадают**. Но отсутствует и политика
   редактирования, а каналы утечки уже есть:
   - `print(...)` в stderr с путём настроек ([main.py:93](main.py:93));
   - алерты показывают `str(exc)` от `python-docx`/`openpyxl` — в тексте бывают
     полные пути, включая имя контрагента ([main.py:3099](main.py:3099), [main.py:3285](main.py:3285));
   - в сборке `console=False`, но `disable_windowed_traceback=False`
     ([`EWDochub.spec:59`](EWDochub.spec:59)) — при необработанном исключении
     PyInstaller показывает диалог с трассировкой (пути, имена файлов);
   - имена файлов в экране импорта содержат названия контрагентов
     ([main.py:3714](main.py:3714));
   - Windows Error Reporting может сохранить дамп процесса, в памяти которого
     находятся реквизиты и ключ.

   При добавлении логирования (рекомендация 9.8, п. 9) **обязательно** ввести
   редактирование: не писать значения полей `F`, ИНН, счета, ключ, полный текст
   документов и полные пути; писать только `id`, тип, размер, результат.

### 10.5. Прочие каналы утечки и особенности поставки

1. **Реальные документы и скриншоты в рабочей папке**: договоры ООО «ЛИДЕР ДВ»
   в корне, [`образцы/`](образцы/), [`preview/`](preview/), [`БАГИ/`](БАГИ/)

2. **Артефакты сборки в проекте**: `build/`, `installer/install.exe` содержат
   код и вшитый ключ; их не следует держать в одной папке с исходниками и тем

   `SignTool`, `EW.DocHub.exe` тоже без подписи → предупреждения SmartScreen,
   невозможность проверить подлинность сборки, риск подмены установщика.
4. **Установка в `Program Files`** ([`installer.iss:15`](installer.iss:15),
   по умолчанию нужны права администратора) — само по себе правильно: данные
   пишутся в профиль пользователя. Но деинсталлятор **не удаляет**
   `%APPDATA%\DogovorGenerator` и `%APPDATA%\DogovorPostavki` — персональные
   данные и ключ остаются на машине после удаления программы.
5. **Общий профиль/роуминг**: `%APPDATA%` может синхронизироваться доменом или
   попадать в корпоративный бэкап — открытый JSON и файл ключа уедут туда же.
6. **Smoke-тест изолирован** — подменяет `APPDATA` на временный каталог
   ([`smoke_test.py:9`](smoke_test.py:9)–[smoke_test.py:10](smoke_test.py:10)),
   поэтому боевой реестр не затрагивает. Это правильная практика.
7. **Нет аутентификации и разграничения ролей** — любой, кто запустил программу
   под учётной записью, видит все реквизиты и банковские счета; для одного
   пользователя это нормально, для общего ПК — нет.

### 10.6. Итоговая оценка безопасности

| Риск | Вероятность | Ущерб | Защита сейчас |
|---|---|---|---|
| Извлечение и злоупотребление вшитым ключом DaData | высокая (ключ в каждой копии) | высокий (квота, расходы, блокировка) | нет |
| Запуск вредоносного файла через «Неопознанные документы» | средняя (нужно выбрать файл самому) | критический (RCE под учётной записью) | нет |
| Открытие импортированного документа без Protected View | высокая | высокий | нет (MOTW стирается) |
| Кража ноутбука/диска: реквизиты и счета в открытом виде | средняя | высокий | только ACL Windows |
| Утечка через скриншоты/образцы/передачу папки проекта | высокая | высокий | нет |
| Подмена ответа DaData → неверные реквизиты в договоре | низкая | высокий | нет (ИНН не сверяется) |
| Утечка через логи | низкая (логов нет) | средний (при добавлении логов) | нет политики редактирования |
| Заполнение диска/исчерпание памяти при импорте | низкая-средняя | средний | нет лимитов |
| Нарушение 152-ФЗ (передача ИНН ИП, хранение без основания) | средняя | юридический | нет документов |

**Общий вывод:** базовая гигиена соблюдена (HTTPS, минимизация запроса, нет
телеметрии, нет SQL/шелла с пользовательским вводом, изолированный smoke-тест),
но **модель безопасности фактически отсутствует**: секрет в коде, данные без
шифрования, импорт без allowlist и с запуском файлов по клику, реальные
документы в поставке. Наиболее опасны два сценария: компрометация общего ключа
DaData и запуск произвольного файла из раздела «Неопознанные документы».

### 10.7. Рекомендации по безопасности

**P0 — устранить критические риски:**

1. **Убрать ключи из кода и сборки**, перевыпустить оба (считать
   скомпрометированными), `SECRET_KEY` удалить полностью — он не используется.
   Ключ вводить в настройках, хранить через DPAPI (`CryptProtectData`) или
   `keyring`, а не в открытом `dadata_key.txt`; предусмотреть замену и удаление
   ключа, маскированный ввод и проверку (запрос баланса/тестовый ИНН).
2. **Allowlist импорта**: разрешить только `.docx`/`.xlsx` (при необходимости
   `.xlsm` — с предупреждением), убрать «Все файлы», не копировать файлы, которые
   не удалось разобрать, для «неопознанных» заменить «Открыть» на «Показать в
   папке», открывать только файлы с проверенным расширением и сигнатурой.
3. **Сохранять Mark-of-the-Web** при копировании (переписывать поток
   `Zone.Identifier`) либо открывать импортированные файлы в Protected View;
   как минимум — явное предупреждение при открытии.
4. **Лимиты импорта**: размер файла (например, 50 МБ), количество файлов,
   суммарный объём, проверка свободного места, таймаут разбора, защита от
   zip bomb (число и суммарный размер распакованных членов).
5. **Не хранить полный текст** импортированных документов в реестре — только
   извлечённые поля и короткий фрагмент; либо шифровать.
6. **Логирование с редактированием**: отдельный модуль, запрет на запись
   значений полей, ИНН, счетов, ключа, полного текста и полных путей; ротация,
   ACL на каталог логов, замена молчаливых `except` на логирование.

**P1 — снизить остаточные риски:**

7. Шифрование данных at rest: DPAPI для `database.json` и ключа (минимум —
   для ключа) или SQLite+SQLCipher; продумать миграцию и восстановление.
8. Предупреждение при выборе папки документов на сетевой/съёмный носитель и
   показ фактических прав доступа.
9. Сверять `data["inn"]` с запрошенным ИНН, добавить `User-Agent`,
   повтор с backoff и ограничение частоты запросов.
10. Убрать из проекта и поставки реальные документы, скриншоты, `build/` и
    `installer/install.exe`; добавить `.gitignore`; если папка публиковалась —
    считать данные раскрытыми.
11. Подписывать `EW.DocHub.exe` и установщик, публиковать SHA-256; не
    распространять сборки с общим ключом.
12. Валидировать имена (длина, резервные имена Windows) и не открывать файлы по
    пути из реестра без проверки, что путь находится внутри папки документов.
13. Оформить обработку персональных данных: основание передачи ИНН в DaData,
    уведомление пользователя, сроки хранения, удаление по запросу (сейчас
    удаление контрагента не удаляет файлы и текст).

**P2:**

15. Аудит действий (открытие/удаление) — при переходе на многопользовательский
    режим.
16. Контроль целостности документов (хэши) — вместе с задачей сверки из

**Вывод:** базовый путь «контрагент → договор» проходим и короток, но содержит
необязательные препятствия: обязательные «необязательные» поля, повторный выбор
контрагента на каждой странице, модальные подтверждения успеха, импорт в
настройках. Ошибки вероятны не в вводе (валидация хорошая), а в **идентификации
объекта** (какой контрагент/договор выбран) и в **необратимых действиях**.

### 11.3. Понятно ли, какой контрагент выбран?

| Место | Что видно | Проблема |
|---|---|---|
| Страницы «Договор», «Доп. соглашение», «Спецификация» | выпадающий список «Название · ИНН» | **три независимых списка**: выбор на одной странице не переносится на другие ([main.py:2769](main.py:2769)–[main.py:2778](main.py:2778)) — приходится выбирать заново и легко ошибиться |
| Список контрагентов | «Название · ИП/Юр. лицо · ИНН», выбранный помечен «●» | при повторном клике выбор снимается и маркер исчезает ([main.py:2517](main.py:2517)–[main.py:2522](main.py:2522)); нет счётчика документов, нет подсветки строки |
| Реестр ↔ формы | выбора нет | выбранный в реестре контрагент **не подставляется** в форму договора; связь «реестр → документ» отсутствует |
| Комбобокс | текст названия и ИНН | длинные названия обрезаются; нет адреса/ОГРН/ID, чтобы различить похожие карточки |
| Дубликаты | две одинаковые строки «ООО Ромашка · ИНН 123…» | [`_party_from_var()`](main.py:2780)–[main.py:2788](main.py:2788) берёт **первую** запись; какая именно выбрана — определить нельзя; ручное создание дубликата по ИНН не блокируется ([`_cp_save()`](main.py:4026)–[main.py:4065](main.py:4065)) |
| После удаления/переименования | в списке остаётся старое значение | [`set_values()`](ui_macos.py:1444)–[ui_macos.py:1446](ui_macos.py:1446) не сбрасывает несуществующий выбор: имя видно, но `_party_from_var` вернёт `None` → «Контрагент не выбран» при видимом названии |
| Импорт | новые карточки создаются по ИНН | при пустом ИНН создаётся новая карточка-«полукопия» (см. 5.4) → в списке появляются почти одинаковые записи |

**Вывод:** в простом случае (один-два контрагента, без дублей) выбор понятен
благодаря названию и ИНН. В реальном реестре — **нет**: нет единого «текущего
контрагента», нет идентификатора в списке, дубликаты неразличимы, а устаревшее
значение может выглядеть выбранным. Нет и явной строки-подтверждения рядом с
кнопкой сохранения («Документ для: …»).

### 11.4. Понятно ли, какие документы будут удалены?

| Операция | Подтверждение | Что показано | Что происходит с файлами | Оценка |
|---|---|---|---|---|
| Удаление документа | **нет** | ничего; кнопка «Удалить» стоит рядом с «Открыть Word» ([main.py:2635](main.py:2635)–[main.py:2642](main.py:2642)) | `.docx` остаётся на диске, запись исчезает | **опасно**: случайный клик безвозвратно убирает запись, отмены нет |
| Удаление контрагента | есть ([`ui.confirm`](ui_macos.py:1934)) | имя и **количество** документов, «Действие нельзя отменить» ([main.py:3300](main.py:3300)–[main.py:3304](main.py:3304)) | записи удаляются, **файлы и папка остаются**; в сообщении это не сказано | частично: нельзя увидеть, **какие** документы (тип, номер, дата) будут удалены |
| Удаление контрагента, который не выбран | есть | только количество | его документы в этот момент **не видны** в интерфейсе — проверить нечего | опасно |
| Удаление «неопознанного» | нет | ничего | файл остаётся в `unknown` | средне |
| Очистка таблицы спецификации | нет | иконка «корзина» ([main.py:1050](main.py:1050)–[main.py:1052](main.py:1052)) | мгновенно очищает все позиции; отмены нет | **опасно для несохранённых данных** |
| Уменьшение «Строк:» | нет | поле количества ([main.py:1054](main.py:1054)–[main.py:1069](main.py:1069)) | по Enter лишние строки уничтожаются вместе с введёнными данными | средне |

Дополнительно: кнопка подтверждения в диалоге — обычная синяя
([`ui_macos.py:1863`](ui_macos.py:1863)), а не «опасная» красная; `Enter` в
диалоге вызывает `_close`, то есть **действует как отмена**
([`ui_macos.py:1873`](ui_macos.py:1873)) — это безопасно, но противоречит
ожиданию «Enter = подтвердить».

**Вывод:** на вопрос «какие документы будут удалены?» интерфейс **не отвечает**:
для документа подтверждения нет вовсе, для контрагента показано только число,
без перечня и без предупреждения, что файлы останутся. Отмены/корзины нет ни для
одного случая.

### 11.5. Ошибки, которые интерфейс провоцирует

1. **Редактируемый предпросмотр, который ни на что не влияет.** Заголовок
   спецификации прямо приглашает: «Текст документа — можно редактировать»
   ([main.py:1943](main.py:1943)), а [`_set_text()`](main.py:2808)–[main.py:2813](main.py:2813)
   оставляет поле редактируемым. Но при сборке `.docx` текст не используется:
   договор сохраняется с `text=""` ([main.py:3086](main.py:3086)), спецификация —
   с текстом, который экспорт игнорирует ([main.py:3232](main.py:3232)). Правки
   молча теряются.
2. **Дубликаты договоров.** Номер не проверяется на уникальность; в списке
   договоров-оснований появляются две строки «№ 5 от 1 января»
   ([main.py:2790](main.py:2790)–[main.py:2793](main.py:2793)) — какая
   подставится в спецификацию, зависит от порядка записей.
3. **Автовыбор первого договора** при смене контрагента
   ([main.py:2270](main.py:2270)–[main.py:2279](main.py:2279),
   [main.py:2429](main.py:2429)–[main.py:2438](main.py:2438)): пользователь может
   не заметить, что доп. соглашение привязано не к тому договору.
4. **Обязательные поля без реальной необходимости** (email, телефон, расчётный
   счёт) вынуждают вводить фиктивные данные — они попадут в документы.
5. **Нет предупреждения о несохранённых данных** при закрытии окна
   ([`close()`](main.py:1854)) и при уходе со страницы: введённый, но не
   сохранённый документ теряется без вопроса.
6. **Модальные алерты после каждого сохранения** ([main.py:3093](main.py:3093))
   прерывают поток и требуют лишнего клика; альтернативы «показать в папке» нет.
7. **Поиск только по ИНН** и только по кнопке: найти контрагента по названию
   нельзя, ввод букв игнорируется ([main.py:2467](main.py:2467)–[main.py:2473](main.py:2473)).
8. **Нет горячей клавиши сохранения** (Ctrl+S) и сохранения по Enter — только
   кнопка в футере; из клавиатурных сокращений есть Ctrl+N, F11, Esc, Alt+F4
   ([main.py:1607](main.py:1607)–[main.py:1614](main.py:1614)).

### 11.7. Доступность и эргономика

- **Клавиатура**: [`ComboField`](ui_macos.py:1358) открывается только кликом
  (`<Button-1>`), не фокусируется по Tab и не открывается с клавиатуры — выбрать
  контрагента без мыши нельзя. Иконочные кнопки [`IconButton`](ui_macos.py:1538) —
  canvas с подсказкой по наведению, без доступного имени.
- **Мелкий текст**: подсказки 11 px, подписи 12 px — на 1366×768 читается, но
  при 100 % масштабе мелко.
- **Минимальный размер окна**: 1120×620 логических пикселей
  ([main.py:66](main.py:66)–[main.py:67](main.py:67),
  [main.py:1571](main.py:1571)–[main.py:1573](main.py:1573)); при масштабе
  125–150 % минимум становится 1400–1680 px и **не помещается** на экран
  1366×768 — контент может обрезаться (требует проверки на реальном ноутбуке).
- **Кастомная рамка окна**: свои кнопки, перетаскивание, ресайз-хэндлы
  ([main.py:1764](main.py:1764)–[main.py:1796](main.py:1796)) — выглядит цельно,
  но нет системного меню окна и привычных сочетаний Windows; для части
  пользователей это непривычно.
- **Модальные окна** забирают ввод (`grab_set`), Esc закрывает; это корректно,
  но при долгом импорте отменить операцию нельзя — только ждать
  ([main.py:3658](main.py:3658)–[main.py:3707](main.py:3707)).

## 12. Анализ производительности: скорость, задержки, зависания интерфейса

### 12.1. Методика и условия замеров

Замеры выполнены на исходниках (не на собранном `.exe`), Windows 11, SSD,
Python 3.13, медиана 2–7 прогонов. Использовались синтетические данные:
контрагенты с полным набором полей, документы со снимком реквизитов, текстом
около 2 тыс. символов и 5 позициями. Реальный `%APPDATA%` не затрагивался —
подменялся временным каталогом (как в [`smoke_test.py:9`](smoke_test.py:9)).
Замерялись: [`DataStore.save()`](storage.py:82)/[`_load()`](storage.py:59),
сборка `.docx` ([`_render_contract_docx()`](main.py:2848),
[`_render_spec_docx()`](main.py:2872)), [`refresh_registry()`](main.py:2524),
открытие [`_ComboPopup`](ui_macos.py:1164), [`set_row_count()`](main.py:1268)
таблицы спецификации.

Побочное наблюдение: в этой среде создание окна упало с
`TclError: bad cursor spec "top_side"` в
[`_install_resize_handles()`](main.py:1764)–[main.py:1796](main.py:1796) —
для UI-замеров ручки ресайза пришлось отключить. Это не производительность, а
риск совместимости сборки Tk; имена курсоров стоит проверить на целевых
машинах.

| `import main` (все библиотеки) | **0,22 с** | customtkinter, python-docx, openpyxl импортируются сразу |
| Создание окна и **всех шести страниц** | **0,72 с** | [`_build_pages()`](main.py:1931) строит всё заранее: две полные формы контрагента (~40 полей), `SpecTable` с 10 строками |
| Загрузка реестра 34 МБ / 5 000 документов | **0,17 с** | [`_load()`](storage.py:59) парсит JSON целиком |
| Загрузка реестра 0,7 МБ / 100 документов | **0,004 с** | |

**Итого холодный старт из исходников ≈ 0,9 с** — приемлемо. В собранном
`.exe` добавятся распаковка/чтение библиотек (обычно +0,5–1,5 с на холодную).
Старт линейно зависит от размера `database.json`: при 200–300 МБ (реально при
большом числе импортированных документов, см. 12.4) загрузка займёт секунды и
столько же памяти.

### 12.3. Поиск и реестр: главный источник зависаний

[`refresh_registry()`](main.py:2524) **уничтожает и создаёт заново все виджеты**
списка: на каждого контрагента — строка-фрейм и три кнопки, на каждый документ —
строка и две кнопки ([main.py:2555](main.py:2555)–[main.py:2642](main.py:2642)).
Замеры перерисовки:

| Реестр | Время перерисовки |
|---|---|
| 100 контрагентов / 300 документов | **0,99 с** |
| 300 контрагентов / 900 документов | **3,07 с** |
| 600 контрагентов / 1 800 документов | **6,07 с** |

Зависимость линейная, ≈10 мс на строку. Перерисовка вызывается **на каждое**
действие: клик по контрагенту (раскрыть/свернуть документы,
[main.py:2517](main.py:2517)–[main.py:2522](main.py:2522)), нажатие «Найти по
ИНН» ([main.py:2509](main.py:2509)), сохранение любого документа
([main.py:3088](main.py:3088), [main.py:3155](main.py:3155),
[main.py:3234](main.py:3234)), удаление ([main.py:3289](main.py:3289),
[main.py:3316](main.py:3316)), импорт ([main.py:3828](main.py:3828)),
сохранение контрагента ([main.py:4060](main.py:4060)).

Следствия:

- **сам поиск по ИНН дешёвый** ([`_registry_parties()`](main.py:2498) — один
  проход по списку), но его результат стоит 1–6 с перерисовки; фильтрация не
  происходит по мере ввода — нужен клик;
- **раскрытие документов** контрагента в большом реестре ощущается как
  зависание: это не запрос, а полная перерисовка;
- при 1 000 контрагентов ожидаемое время — **≈10 с на одно действие**;
- в футере [`_update_status()`](main.py:4198) дополнительно проходит все
  документы, но это доли миллисекунды на фоне виджетов.

**Выпадающий список** [`_ComboPopup`](ui_macos.py:1164) создаёт по `tk.Label`
на **каждое** значение при открытии:

| Список | Время открытия |
|---|---|
| 1 000 контрагентов | **0,50 с** |
| 5 000 (экстраполяция) | **≈2,5 с** |

Хуже: [`_set_index()`](ui_macos.py:1238)–[ui_macos.py:1250](ui_macos.py:1250)
при наведении мыши перекрашивает **все** строки списка — при 1 000 пунктов
каждое движение между строками даёт O(n) перерисовок. Виртуализации и поиска
внутри списка нет. Обновление значений в трёх комбобоксах, наоборот, дешёвое
(замер: ~0 мс на 1 000) — проблема только в открытии.

### 12.4. Сохранение документов и размер реестра

Каждое изменение вызывает [`save()`](storage.py:82), который **сериализует и
перезаписывает весь JSON** (с `indent=2`) в потоке интерфейса:

| Реестр | Размер файла | Время `save()` |
|---|---|---|
| 50 контрагентов / 100 документов | 0,7 МБ | **14 мс** |
| 500 / 1 000 | 7,0 МБ | **95 мс** |
| 2 000 / 5 000 | 34,2 МБ | **454 мс** |

Полный цикл сохранения договора = `add_document()` (полная запись JSON) +
[`refresh_registry()`](main.py:2524) (1–6 с) + сборка `.docx` (см. 12.5) +
открытие Word. При реестре 600 контрагентов это **6–7 секунд «замороженного»
интерфейса** на одно сохранение, при 100 — около 1 с.

Размер файла растёт линейно и **удваивается за счёт снимков реквизитов**: каждый
документ хранит копию `data` ([storage.py:169](storage.py:169)) и текст до
100 000 символов ([`TEXT_KEEP_LIMIT`](document_importer.py:54),
[document_importer.py:502](document_importer.py:502)). Оценка: 1 000
импортированных документов со средним текстом 50 тыс. символов — это
**порядка 100–200 МБ** JSON; каждое сохранение будет писать столько же, а
загрузка — парсить. `indent=2` добавляет ещё 20–30 % объёма.

### 12.5. Массовый импорт: анализ быстрый, регистрация — узкое место

| Этап | Время | Поток |
|---|---|---|
| Анализ одного `.docx` ([`analyze_file()`](document_importer.py:483)) | **19 мс** | фоновый — правильно |
| Копирование файла ([`_copy_imported_file()`](main.py:3726)) | зависит от диска | фоновый |
| Регистрация результатов ([`_finish_documents_import()`](main.py:3783)) | **864 мс на документ** | **поток интерфейса** |

Замер: 50 добавлений в реестр из 5 000 документов заняли **43,2 с** (0,86 с на
запись при одном сохранении 0,44 с). Причина — на каждый файл вызываются
[`add_counterparty()`](storage.py:111) (если контрагент новый) и
[`add_document()`](storage.py:153), и **каждый** делает полную запись JSON.
Для 200 импортируемых файлов это:

- 200–400 полных перезаписей файла (если все контрагенты новые);
- **≈3 минуты** работы в потоке интерфейса без прогресса и возможности отмены;
- суммарно записанные байты растут **квадратично** числу файлов (каждый раз
  пишется весь реестр), то есть O(N²).

Окно прогресса к этому моменту уже закрыто ([main.py:3770](main.py:3770)–[main.py:3775](main.py:3775)),
поэтому пользователь видит «зависшее» приложение и, скорее всего, завершит его
— что приводит к файлам-сиротам и потерянным записям (раздел 9.2).

### 12.6. Где именно зависает интерфейс

| Действие | Что выполняется в UI-потоке | Задержка (замер/оценка) |
|---|---|---|
| Сохранение договора/доп./спецификации | запись всего JSON + полная перерисовка реестра + сборка `.docx` | 1–7 с (растёт с реестром) |
| Удаление документа/контрагента | запись JSON + полная перерисовка | 1–7 с |
| Клик по контрагенту в реестре | полная перерисовка | 1–6 с |
| «Найти по ИНН» | полная перерисовка | 1–6 с |
| Завершение импорта | N × (запись JSON + поиск по ИНН) | десятки секунд — минуты |
| Установка «Строк: 500» в спецификации | создание 2 000+ виджетов ячеек | **9,87 с** |
| Ввод в предпросмотре договора | сборка `.docx` + извлечение текста (через 120 мс) | 48 мс на паузу |
| Ввод в таблице спецификации | пересборка текста и полная замена текстового поля | единицы–десятки мс |
| Запрос DaData | сеть в фоновом потоке, спиннер | интерфейс не блокируется |
| Анализ файлов при импорте | фоновый поток + очередь | интерфейс не блокируется |

Таблица спецификации: 10 строк по умолчанию создаются сразу при старте
([main.py:1116](main.py:1116)–[main.py:1117](main.py:1117)); `set_row_count(500)`
создаёт по 5 виджетов на строку и занимает **почти 10 секунд** — интерфейс
полностью замирает. Разбор 500 строк при вводе дешёвый (2 мс), поэтому
тормозит именно создание/удаление строк, а не расчёты.

Предпросмотр: обновление отложено на 120 мс
([`_preview_contract()`](main.py:2076)–[main.py:2083](main.py:2083)), но каждая
перерисовка заново читает шаблон с диска и строит документ
([`Document(template_path)`](main.py:2850)) — 48 мс; кэша шаблонов нет.
`_regenerate_spec()` для спецификации **не имеет дебаунса** и вызывается на
каждое изменение позиции/даты/условий
([main.py:2307](main.py:2307), [main.py:2333](main.py:2333),
[main.py:2353](main.py:2353)–[main.py:2354](main.py:2354),
[main.py:2396](main.py:2396)–[main.py:2398](main.py:2398)) — на 500 строках это
ощутимый стук на каждый символ.

### 12.7. Что работает быстро

- **Сетевой запрос DaData** — в отдельном потоке ([main.py:4091](main.py:4091)),
  таймаут 10 с, спиннер; UI не замирает.
- **Анализ импортируемых файлов** — фоновый поток и очередь
  ([`_import_worker()`](main.py:3709), [`_import_tick()`](main.py:3749));
  один документ — 19 мс.
- **Валидация и форматирование** — мгновенные, на каждый ввод.
- **Вставка позиций из Excel** — один пакетный проход с подавлением
  промежуточных обновлений ([`_batch`](main.py:1035)).
- **Пересчёт сумм/НДС** — доли миллисекунды (2 мс на 500 строк).
- **Загрузка реестра до десятков мегабайт** — 0,17 с.

### 12.8. Оценка масштабируемости

| Объём | Ожидаемое поведение |
|---|---|
| до 100 контрагентов, до 300 документов | работает, перерисовка ≈1 с — заметно, но терпимо |
| 300 / 900 | 3 с на любое действие с реестром — раздражает, провоцирует повторные клики |
| 600 / 1 800 | 6 с — субъективно «программа зависла» |
| 1 000+ / 5 000 | 10 с и более; импорт сотен файлов — минуты; риск принудительного завершения |
| 500 строк спецификации | 10 с на изменение количества строк |
| реестр > 100 МБ (много импортированных текстов) | секунды на старт и на каждое сохранение, высокий расход памяти |

**Вывод:** приложение быстро работает «на старте» и на малых объёмах, но
**не масштабируется по числу контрагентов и документов**. Узкие места — полная
перерисовка реестра, полная перезапись JSON на каждую операцию, регистрация
импорта в UI-потоке и создание виджетов на каждую строку таблицы.

### 12.9. Рекомендации по производительности

**P0 — убрать зависания:**

1. **Перестать перерисовывать весь реестр.** Обновлять только изменившуюся
   строку/секцию, а список строить виртуализированно (переиспользование строк
   при прокрутке) или страницами по 50–100. Раскрытие документов и поиск не
   должны пересоздавать всех контрагентов.
2. **Не писать весь JSON на каждую операцию.** Перейти на SQLite (WAL,
   индексы по ИНН и `party_id`) либо, как минимум, батчить сохранения:
   отложенная запись (debounce 300–500 мс) в фоновом потоке, один `save()` на
   пакет импорта, транзакция на `_finish_documents_import`.
3. **Регистрацию импорта вынести в фон** с прогрессом, отменой и одним
   сохранением в конце; сейчас это N полных записей в UI-потоке.
4. **Комбобокс**: не создавать `tk.Label` на каждый пункт, ограничить список
   (например, 100 + поиск/скролл), убрать O(n) перекраску в
   [`_set_index()`](ui_macos.py:1238).
5. **Таблица спецификации**: виртуализация или `Treeview`, ограничение числа
   строк; не создавать 500 строк виджетов одним вызовом.

**P1 — снизить задержки:**

6. Кэшировать загруженные шаблоны `Document` в памяти — сейчас каждый
   предпросмотр читает `.docx` с диска.
7. Дебаунс для `_regenerate_spec()` (как у предпросмотра договора) и обновление
   только итогов, а не всего текстового поля.
8. Ленивая сборка страниц (строить при первом открытии) — сократит старт и
   память; `SpecTable` создавать при переходе на страницу.
9. Индикатор занятости (курсор/оверлей) и блокировка повторных кликов на время
   сохранения/удаления, чтобы пользователь не запускал операцию дважды.
10. Не хранить полный текст документов в реестре (или хранить отдельно/сжато):
    это главный драйвер размера JSON и времени сохранения.
11. Убрать O(n²) в [`replace_in_paragraph()`](main.py:700) (пересборка текста
    абзаца на каждую замену) — один проход вместо повторных `rebuild_full_text`.
12. Замерять и логировать операции дольше 500 мс (медленное сохранение,
    перерисовка, импорт).

**P2:**

13. Перейти на SQLite с `synchronous=NORMAL` и индексами — заодно решатся
    атомарность и конкурентный доступ (разделы 9.3, 9.4).
14. Добавить тест производительности на синтетическом реестре (100 / 1 000 /
    5 000 документов) в CI, чтобы регрессии были видны сразу.
15. Проверить и заменить имена курсоров вида `top_side` на стандартные

### 13.1. Что считается целевыми условиями

Явно целевая ОС нигде не заявлена: в README нет раздела о поддерживаемых
Windows/Word, установщик не ограничивает версию ОС, а `ui_macos.py` — это только
оформление, а не поддержка macOS. Фактически приложение **Windows-only**:
используются `%APPDATA%` ([storage.py:35](storage.py:35)), `os.startfile`
([main.py:689](main.py:689)), Win32/DWM-вызовы
([ui_macos.py:164](ui_macos.py:164)–[ui_macos.py:279](ui_macos.py:279)) и
`customtkinter.windows...` ([main.py:33](main.py:33)). Разумная целевая
конфигурация: **Windows 10/11 x64, Word 2007+ (или LibreOffice), обычный
пользовательский профиль с правом записи в `%APPDATA%`**.

| Свойство | Факт | Следствие |

**Мониторы и DPI.** Приложение объявляет per-monitor DPI awareness
([main.py:45](main.py:45)–[main.py:52](main.py:52)) и считает масштаб один раз
при старте ([main.py:1558](main.py:1558)–[main.py:1559](main.py:1559)).

масштабом интерфейс не пересчитается (текст/отступы могут «поплыть»).

мультимониторной конфигурации максимизация всегда уходит на основной экран.
Безрамочное окно (`overrideredirect`) не участвует в системном Snap (Win+стрелки)
и Snap Layouts Windows 11.

### 13.5. Отсутствие Word

**Генерация документов от Word не зависит** — `.docx` собирается через
`python-docx` из шаблонов, Word нужен только для просмотра/правки. Это сильная
сторона: файлы создаются и на машине без Office.

Проблемы начинаются при открытии:

1. [`open_file()`](main.py:687)–[main.py:696](main.py:696) вызывает
   `os.startfile`. Если `.docx` ни с чем не связан, Windows либо показывает
   диалог «Чем открыть файл?», либо `os.startfile` бросает `OSError`; в первом
   случае пользователь может закрыть диалог, во втором — увидит алерт
   «Не удалось открыть файл».
2. После этого [`save_contract()`](main.py:3093)–[main.py:3098](main.py:3098)
   **всё равно** показывает успех с текстом «Открыт в Word: <путь>» — сообщение
   неверно, если открытие не удалось или файл открылся в LibreOffice.
3. Нет кнопки «Показать в папке» и «Сохранить как…» в этом сценарии: путь есть
   только текстом в алерте, скопировать его из модального окна нельзя.
4. Папка по умолчанию — `%APPDATA%\DogovorGenerator\documents`
   ([main.py:2825](main.py:2825)–[main.py:2830](main.py:2830)), то есть скрытый
   AppData. Word может открыть такой файл в режиме защищённого просмотра
   (зависит от настроек и политик), а пользователю труднее найти документы.
   Для совместимости лучше по умолчанию `Документы\EW.DocHub`.
5. Word 2003 и старше `.docx` без пакета совместимости не откроют; LibreOffice,
   «МойОфис», Google Docs — откроют, если настроена ассоциация.
6. Проверки наличия Word/ассоциации при установке или первом запуске нет; нет
   экспорта в PDF как запасного варианта.

### 13.6. Кириллица и пути

**Подтверждено на практике:** среда анализа находится в каталоге
`C:\Users\Эдик\Desktop\Суцко\code\Договор поставки\...` — запись и чтение
`database.json`, сборка `.docx`, работа UI и импорт выполнялись без ошибок.
JSON пишется в UTF-8 с `ensure_ascii=False` ([storage.py:88](storage.py:88)–[storage.py:97](storage.py:97)),
файлы открываются с `encoding="utf-8"`, `os.startfile` корректно работает с
юникод-путями. Кириллица в именах контрагентов и файлов сохраняется
([`safe_filename()`](main.py:1001)–[main.py:1007](main.py:1007)).

Ограничения и риски:

| Ситуация | Что происходит |
|---|---|
| Длинное имя контрагента + глубокая папка | длина пути не контролируется; при превышении `MAX_PATH` (260) `doc.save()` падает с `OSError`, либо [`_party_documents_dir()`](main.py:2842)–[main.py:2845](main.py:2845) молча возвращает корень папки документов |
| Имя контрагента `..` или `.` | [`safe_filename()`](main.py:1001) не фильтрует точки: папка `documents\..` выводит запись **за пределы** каталога документов |
| Имена `CON`, `PRN`, `NUL`, `COM1`, имена с точкой/пробелом на конце | создание папки может упасть или Windows нормализует имя; документы попадут в корень или возникнет коллизия |
| `ООО Ромашка` и `ООО ромашка` | Windows не различает регистр — обе карточки пишут в одну папку, документы смешиваются |
| Сетевая папка или OneDrive | работает, но возможны задержки, блокировки файлов и конфликты синхронизации; предупреждения нет |
| Роуминг-профиль (`%APPDATA%` на сервере) | каждая запись JSON идёт по сети; `os.replace` может падать при блокировке; данные и ключ копируются на сервер |
| Консольные скрипты (`smoke_test.py`, замеры) | в консоли cp1251 русский вывод превращается в «кракозябры» (наблюдалось при замерах); GUI это не затрагивает, но при добавлении логов нужен UTF-8 |

### 13.7. Прочие условия эксплуатации

- **Нет интернета**: приложение работает, DaData выдаёт понятную ошибку
  «Нет соединения»; ручной ввод доступен. Офлайн-кэша реквизитов нет.
- **Нет прав на запись в `%APPDATA%`** (обязательный профиль, политики):
  реестр молча пуст, сохранения не пишутся (раздел 9.4); режима «только
  чтение» и понятного сообщения нет.
- **Нет прав администратора**: установка невозможна (admin по умолчанию), но
  папочную сборку `dist\EW.DocHub` можно скопировать и запустить без установки —
  это не описано в README.
- **Портативный режим**: не поддерживается — данные всегда в `%APPDATA%`
  текущего пользователя, на флешке они не сохраняются.
- **Локализация**: интерфейс и печатные формы только на русском; названия
  месяцев и формат сумм захардкожены (это нормально для РФ), десятичная запятая
  принимается.
- **Шрифты**: используется Segoe UI и fallback из Tk; на урезанных сборках
  Windows без шрифтов интерфейс может выглядеть иначе, но не падает.
- **Высокая контрастность/спецвозможности**: собственная палитра игнорирует
  системную тему высокой контрастности.
- **Логи и диагностика**: `console=False` ([`EWDochub.spec:58`](EWDochub.spec:58)),
  файла лога нет; на целевой машине причину сбоя установить нечем (раздел 9.7).
- **Обновление**: механизма нет; пользователи остаются на версии 1.3, пока им
  вручную не передадут новый `install.exe`; схема данных не версионирована,
  откат на старую версию может быть несовместим.
- **Лицензии**: в установщике нет текстов лицензий сторонних библиотек
  (customtkinter — MIT, python-docx — MIT, openpyxl — MIT, Pillow — HPND,
  lxml — BSD); для распространения это формальное требование.

Тест подтверждает только **наличие подстрок** в абзацах собранного документа:
название контрагента, ФИО директора, номер и одна таблица
([smoke_test.py:163](smoke_test.py:163)–[smoke_test.py:169](smoke_test.py:169)).
Этого достаточно, чтобы поймать грубую поломку (`Document(template)` не
открылся, замены не применились), но **недостаточно для приёмки печатной
формы**:

- нет сравнения с эталонами из [`образцы/`](образцы/) и корня проекта;
- нет проверки, что в результате **не осталось** `{{...}}` — опечатка в шаблоне
  или незаменённый токен пройдёт незамеченным;
- **спецификация вообще не собирается в `.docx`** в тесте: проверяется только
  текстовый предпросмотр, поэтому подтверждённый баг с `{{KPP}}`/`{{OGRN}}`
  у ИП (раздел 5.2) тест **не ловит**;
- нет ИП ни в одном сценарии: `is_ip=True` не проверяется ни для договора, ни
  для доп. соглашения, ни для спецификации;
- не проверяются таблица реквизитов договора (только её наличие), таблица
  подписей, лимит/срок в доп. соглашении, позиции и НДС в спецификации;
- не проверяются плейсхолдеры, разбитые на runs, гиперссылки и колонтитулы
  (риски из раздела 5.3).

### 14.4. Проверки сохранения: проверяется память, а не диск

После `save_contract()`, `save_additional()` и `save_spec()` тест смотрит
**только длину и тип записей в `app.store`**. Ни разу не проверяется:

- существует ли созданный `.docx` по пути из `OPENED` (список собирается, но
  **не используется** — [smoke_test.py:28](smoke_test.py:28)–[smoke_test.py:29](smoke_test.py:29));
- открывается ли файл как документ Word и содержит ли он ожидаемые данные;
- что `database.json` действительно записан и содержит новую запись;
- что `storage.DataStore()` после перезапуска видит те же данные;
- что `save()` вернул `True` (в приложении результат игнорируется — раздел 7.1);
- что снимок реквизитов сохранён в документе;
- что при ошибке записи пользователю показано правильное сообщение (алерты
  складываются в `ALERTS`, но **ни один не проверяется**).

То есть сценарий «сохранение» проверен на уровне «запись появилась в списке»,
а не «данные надёжно сохранены и восстановимы».

### 14.5. Проверки импорта: один синтетический договор

Покрыто: синхронизация ключей полей, три строки для `detect_kind()`, один
искусственный `.docx` с чистыми реквизитами (ИНН, КПП, ОГРН, «Р/с …») и
нераспознанный `.docx` ([smoke_test.py:100](smoke_test.py:100)–[smoke_test.py:130](smoke_test.py:130)).

Не покрыто:

- **реальные образцы** из [`образцы/`](образцы/) и корня — а именно на них
  выявлены проблемы с расчётным счётом и «хвостом» названия (раздел 5.4);
- импорт `.xlsx` (при том, что `openpyxl` — обязательная зависимость);
- доп. соглашение и спецификация как импортируемые файлы;
- дубликаты ИНН и создание «полукопий» контрагентов;
- неполные реквизиты (`recognized=True` при пустом ИНН);
- `.doc`, `.docm`, битые и огромные файлы;
- полный поток: `_import_worker` → `_copy_imported_file` →
  `_finish_documents_import`, папка `unknown`, повторный импорт, закрытие
  во время импорта.

### 14.6. Проверки восстановления после ошибки

**Отсутствуют полностью.** Нет ни одного теста на:

- повреждённый/пустой `database.json` (мусор, обрезанный JSON,
  `"counterparties": null`, `id: null`, дубли `id`);
- восстановление из `database.json.tmp`;
- `save()`, вернувший `False`, и реакцию UI;
- недоступную папку данных/документов (read-only, нет прав, занятый файл);
- отсутствующий `.docx` и пересборку из записи через
  [`export_document()`](main.py:3251) / [`_build_record_docx()`](main.py:2948);
- осиротевшие файлы и сверку «реестр ↔ папка документов»;
- аварийное завершение и частично записанный файл.

Именно эти сценарии описаны в разделах 9.2–9.4 как реальные риски потери
данных, и именно они не проверяются.

### 14.7. Что этот тест не поймал бы (по уже найденным дефектам)

1. Спецификация для ИП с `{{KPP}}`/`{{OGRN}}` — потому что печатная форма
   спецификации не собирается и ИП не тестируется.
2. Любой незаменённый плейсхолдер или опечатку в шаблоне.
3. Неверный НДС или итог в печатной форме — проверяется только предпросмотр.
4. Молчаливую потерю реестра при повреждённом JSON и уничтожение файла первым
   `save()`.
5. «Сохранено» при неудачной записи (`save()` игнорируется).
6. Файлы-сироты после сбоя импорта и несоответствие реестра папке.
7. Дубликаты ИНН/номеров договоров и автоподстановку «не того» договора.
8. Ошибки импорта реальных документов (расчётный счёт, название с «именуемый в
   дальнейшем»).
9. Импорт `.xlsx` и падение при отсутствии `openpyxl`.
10. Отсутствие Word: `open_file` подменён заглушкой, поэтому сценарий
    «открыть не удалось» не проверяется.
11. Удаление документа без подтверждения и то, что файлы остаются на диске.
12. Path traversal (`..`), резервные имена, длинные пути.
13. Запуск произвольного файла из раздела «Неопознанные».
14. Зависания на больших реестрах и массовом импорте.
15. Проблемы сборки: отсутствующий шаблон, `openpyxl`, неверный `resource_path`
    в `.exe`.

### 14.8. Качество самого теста

**Сильные стороны:** изоляция `APPDATA` до импорта приложения
([smoke_test.py:10](smoke_test.py:10)), заглушки модальных окон и `open_file`
(тест не висит и не открывает Word), проверка реальных виджетов и сценариев
сохранения, быстрый прогон, единый и читаемый файл.

**Слабые стороны:**

- **фиксированный временный каталог** и удаление только `database.json`:
  `settings.json`, папка документов и импортированные файлы остаются между
  прогонами — тест не полностью детерминирован;
- **выход на первой ошибке** (`sys.exit(1)` в `check()`): нет полного списка
  проблем и контекста;
- **собранные, но не проверяемые данные**: `ALERTS` и `OPENED` не используются
  в утверждениях — тест не проверяет ни сообщения, ни пути к файлам;
- **monkey-patching без контракта**: замена `ui.alert`/`ui.confirm`/`open_file`
  лямбдами скрывает изменение сигнатур и ошибки в этих вызовах;
- **тест обходит ключевые пути**: `_build_record_docx`/`export_document`,
  `_save_and_open_document` (частично), `_load`, `_finish_documents_import`,
  `close()`/`write_settings` не проверяются;
- **GUI-зависимость**: без рабочего стола/дисплея тест не запустится, для CI
  нужен Windows-раннер с интерактивной сессией;
- **нет структуры**: один монолитный скрипт, нет фикстур, параметризации,
  покрытия и отчёта; нет `requirements-dev.txt`.

### 14.9. Оценка убедительности

| Аспект | Оценка | Почему |
|---|---|---|
| Основной happy path (создать → сохранить → увидеть в реестре) | ⚠️ средне | 93 проверки, реальные виджеты, но только память |

## 16. Итог

- **«Понятно ли, что программа должна делать?» — да**, для разработчика и текущего
  состояния проекта — достаточно. Архитектура и сценарии читаются из README и кода.
- **«Какой результат считается правильным?» — частично.** Для низкоуровневой логики
  критерии есть (smoke-тест); для главных бизнес-результатов — соответствие печатных
  форм образцам, корректность сумм/НДС, точность импорта — критерии не формализованы.
- **«Правильно ли реализованы нужные возможности?» — в основном да**: все печатные
  формы для ООО собираются корректно, суммы/НДС считаются по правилам 1С, реестр и
  хранилище работают, импорт распознаёт типы документов на реальных образцах.
  Найден один подтверждённый дефект (спецификация ИП) и слабые места импорта.
- **«Надёжность и восстановление» — слабое место** (раздел 9). Запись реестра
  атомарна, но чтение не защищено: повреждённый `database.json` молча становится
  пустым реестром и уничтожается первым сохранением. Результат `save()` нигде не
  проверяется, резервных копий, блокировки второго экземпляра и логов нет, `.docx`
  пишется неатомарно, сверки «реестр ↔ папка документов» нет. Сгенерированные
  документы восстановимы из реестра; реестр при повреждении — только из внешней
  копии.
- **«Безопасность» — критическое слабое место** (раздел 10). Ключи DaData вшиты
  в код и попадают в каждую сборку; реквизиты, банковские счета и текст
  документов лежат в открытом JSON; импорт принимает файлы любых расширений и
  позволяет запустить их по клику из раздела «Неопознанные документы»; при
  копировании стирается Mark-of-the-Web; реальные документы и скриншоты лежат
  в папке проекта. Логов нет, поэтому реквизиты в них пока не попадают, но
  политика редактирования отсутствует.
- **«Удобство» — рабочее, но с опасными пробелами** (раздел 11). Основной путь
  «контрагент → договор → спецификация» проходим, валидация и подсказки хороши.
  Но нет единого выбранного контрагента, удаление документа происходит без
  подтверждения, при удалении контрагента не видно перечня документов и не
  сказано, что файлы остаются; предпросмотр редактируется, но правки не попадают
  в `.docx`; поиск только по ИНН; нет Ctrl+S и отмены действий.
- **«Производительность» — приемлема на малых объёмах и деградирует линейно**
  (раздел 12). Старт ≈0,9 с, анализ импорта 19 мс/файл, но перерисовка реестра
  занимает 1 с при 100 контрагентах и 6 с при 600; каждое сохранение переписывает
  весь JSON (34 МБ — 0,45 с), а регистрация импорта идёт в UI-потоке (0,86 с на
  документ, сотни файлов — минуты). Таблица спецификации на 500 строк создаётся
  почти 10 с.
- **«Совместимость и установка» — работает в типовой конфигурации, но не
  заявлена и не защищена** (раздел 13). Windows 11 x64 с Word и кириллическим
  профилем — подтверждено; чистая машина без Python, скорее всего, заработает
  (сборка папочная). Но установщик и exe не подписаны, версия exe пустая,
  установщик не ограничивает 32-битную и старую Windows, без Word сообщение
  «Открыт в Word» неверно, а пути длиннее 260 символов и имя контрагента `..`
  не обрабатываются.
- **«Тесты» — есть только smoke, а не доказательство корректности** (раздел 14).
  93 проверки проходят, но покрывают happy path: генерация проверяется
  подстроками без эталонов и без ИП, сохранение — только в памяти, импорт — на
  одном синтетическом `.docx`, восстановление после ошибок, безопасность,
  производительность и сборка не тестируются. Найденные дефекты (ИП-спецификация,
  потеря реестра, дубликаты, `.xlsx`, отсутствие Word) тест не обнаруживает.
- **«Документация» — частично устарела и не покрывает эксплуатацию** (раздел 15).
  README верно описывает назначение и генерацию, но интерфейс описан от старой
  версии (меню «Файл», боковое меню, четыре страницы, автооткрытие при первом
  запуске), удаление документов и открытие в Word описаны неточно. Инструкций по
  резервному копированию и восстановлению нет вообще; установка описана одной
  строкой без требований, прав администратора и SmartScreen; зависимости для
  сборки неполные.
