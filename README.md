# EW.DocHub (версия 2.14.0)

Настольное приложение на Python для работы с контрагентами и документами:
договоры поставки, доп. соглашения и спецификации формируются из шаблонов
`.docx` по реквизитам контрагента. Реестр контрагентов и созданных документов
хранится локально, интерфейс оформлен в стиле macOS, тема — светлая и тёмная.

## Возможности

* **Карточка контрагента** — юр. лицо или ИП: коды (ИНН, КПП, ОГРН/ОГРНИП),
  названия, руководитель, адреса, контакты и банковские реквизиты.
  Автозаполнение по ИНН через сервис DaData (нужен интернет и API-ключ).
* **Редактирование контрагента** — кнопка «Редактировать» в реестре открывает
  окно с полями карточки и кнопками «Сохранить»/«Отмена». Изменяется только
  карточка: **ранее созданные документы остаются без изменений**, так как
  каждый документ хранит собственную копию реквизитов на момент создания.
* **Договор поставки, доп. соглашение, спецификация** — печатная форма
  собирается напрямую из шаблона `.docx`, форматирование не «плывёт».
  Готовый файл сохраняется в папку контрагента и открывается в Word —
  если Word или LibreOffice установлен и `.docx` с ним ассоциирован.
  Если открытие не удалось, программа честно сообщает «сохранён» (без
  ложного «и открыт») и даёт кнопки «Открыть файл» / «Показать в папке».
* **Реестр** — список контрагентов с поиском по названию и ИНН по мере ввода;
  по выбранному контрагенту видны все его документы. Контрагента можно
  отредактировать или удалить: **записи переносятся в корзину, файлы на
  диске остаются** (восстановление — в разделе «Корзина» реестра).
* **Добавить документы** — загрузка готовых `.docx`/`.xlsx`: программа в фоне
  определяет тип документа и контрагента (поиск по ИНН, иначе создание новой
  карточки после подтверждения) и добавляет их в реестр. Неопознанные файлы
  попадают в папку `unknown` и показываются в реестре отдельным разделом.
* **Настройки** — тема оформления (светлая/тёмная), папка для сохранения
  документов, кнопки «Выбрать папку…», «Открыть папку» и «Добавить документы…»;
  там же задаётся ключ DaData.

Интерфейс: разделы — кнопки в шапке окна («Добавить контрагента», «Договор
поставки», «Доп. соглашение», «Спецификация», «Реестр», «Настройки»); своя
рамка окна со «светофором» справа, перетаскивание за шапку, двойной клик —
развернуть/восстановить. При первом запуске автоматически открывается
добавление контрагента.

## Где хранятся данные

| Путь | Что там |
|---|---|
| `%APPDATA%\DogovorGenerator\database.db` | **Реестр** — источник правды: контрагенты и документы (SQLite) |
| `database.db-wal`, `database.db-shm` | Служебные файлы WAL-журнала (существуют при работе программы) |
| `database.db.bad-…` | Копия повреждённой базы перед восстановлением |
| `database.json.migrated` | Старый JSON-реестр, перенесённый в базу при обновлении |
| `%APPDATA%\DogovorGenerator\settings.json` | Настройки (тема, папка документов, константы спецификации) |
| `%APPDATA%\DogovorGenerator\dadata_key.txt` | Ключ DaData (на Windows шифруется DPAPI) |
| `%APPDATA%\DogovorGenerator\logs\app.log` | Технический журнал (без реквизитов) |
| `Документы\EW.DocHub\<контрагент>\` | Файлы документов (по умолчанию; папка меняется в настройках) |
| `Документы\EW.DocHub\unknown\` | Неопознанные при импорте файлы |

Реестр (`database.db`) — источник правды: имена папок на диске служебные.
Удаление записи в реестре не удаляет файл на диске и наоборот.

## Установка и обновление

* Требования: Windows 10/11 x64; Word или LibreOffice — для открытия готовых
  `.docx`; интернет — для автозаполнения по DaData (без него всё остальное
  работает).
* Запустите `installer\EW.DocHub-2.14.0-setup.exe`. Установщик предложит
  «для всех пользователей» или «только для меня», покажет страницу лицензии
  и уведомлений о сторонних библиотеках, поставит ярлык в меню «Пуск»
  (и по желанию на рабочий стол). Если программа запущена, установщик
  предложит её закрыть (защита от записи в открытый реестр).
* Файл не подписан сертификатом: SmartScreen может показать предупреждение —
  «Подробнее → Выполнить в любом случае». Подписание кодом и публикация
  SHA-256 — организационный шаг при наличии сертификата.
* Тихая установка: `EW.DocHub-2.14.0-setup.exe /VERYSILENT`.
* Обновление: просто запустите установщик новой версии поверх — данные в
  профиле пользователя сохраняются.
* Удаление — «Панель управления → Программы»: деинсталлятор спросит, удалить
  ли настройки, реестр, журнал и ключ DaData. **Папка документов
  `Документы\EW.DocHub` не удаляется** — файлы остаются у пользователя.

## Запуск из исходников

Требуется Python 3.13.

```powershell
python -m pip install -r requirements.txt
python main.py
```

## Тесты

* **pytest — быстрый набор без интерфейса** (153 теста, ~3 секунды,
  GUI не создаётся):

```powershell
python -m pip install -r requirements.txt -r requirements-dev.txt
python -m pytest tests/
```

  Покрывает: golden-сверку шести печатных форм с эталонами (включая
  отсутствие незаполненных `{{...}}` — регрессию бага ИП-спецификации),
  запись «на диск, а не в память», восстановление реестра (битый JSON,
  `.tmp`, `.bad`, отказ ОС в записи, осиротевшие файлы), импорт на образцах
  (ООО/ИП, дубликаты ИНН, `.doc`, битые файлы), DaData с моком сети
  (включая TLS-ошибки и шифрование ключа DPAPI), валидаторы таблицы
  позиций, сбор данных форм с фейковыми виджетами (старт покрытия UI-слоя),
  `safe_filename`, XXE-настройки парсера, allowlist импорта, негативную
  логику. Покрытие модулей: `document_builder` 93 %, `services` 80 %,
  `document_importer` 80 %, `storage` 80 % (цель ≥ 70 %); начат рост
  покрытия `main.py`.

* **Golden-эталоны печатных форм** — `tests/golden/*.json`. Если изменение
  шаблона или подстановок осознанное: `python tests/make_golden.py` и коммит
  эталонов вместе с изменением.

* **smoke_test.py — быстрая проверка интерфейса и логики без ручного
  кликанья** (306 проверок, сводка всех неудач в конце). Нужен дисплей
  или Xvfb:

```powershell
python smoke_test.py                       # Windows
xvfb-run -a python smoke_test.py           # Linux
```

* **CI** — `.github/workflows/ci.yml` (GitHub Actions, Python 3.13):
  Linux — pytest + smoke под Xvfb, Windows — pytest + smoke в графической
  сессии раннера (целевая платформа проверяет GUI-инварианты до релиза).

* **Сборка релиза** — `.github/workflows/release.yml`: по тегу `v*` или
  вручную — pytest, smoke, PyInstaller, Inno Setup и SHA-256 установщика
  в артефактах. Подпись сертификатом — организационный шаг (инструкции
  в шапке `installer.iss`).

* **Проверка собранного .exe (вручную, на Windows):** собрать по инструкции
  ниже или взять артефакт release-workflow → установить на чистую
  Windows 10/11 x64 → запустить `EW.DocHub.exe`,
  создать контрагента и документ → деинсталлировать, убедиться, что
  деинсталлятор спросил про данные и оставил папку документов.

## Сборка и установщик

Сборка делается в два шага (требуются PyInstaller и Inno Setup):

```powershell
python -m pip install -r requirements.txt -r requirements-dev.txt
python -m pytest tests/        # убедиться, что всё зелёное

# 1. Папочная сборка приложения (быстрый запуск, ничего не распаковывается)
pyinstaller --noconfirm EWDochub.spec

# 2. Установщик «EW.DocHub-2.14.0-setup.exe» с ярлыками
#    (Inno Setup: https://jrsoftware.org/isinfo.php)
& "C:\Program Files\Inno Setup 7\ISCC.exe" installer.iss
```

Результаты:

* `dist\EW.DocHub\` — папочная сборка: `EW.DocHub.exe` стартует почти мгновенно;
* `installer\EW.DocHub-2.14.0-setup.exe` — установщик: ставит приложение,
  создаёт ярлыки, показывает лицензию и уведомления о сторонних библиотеках.

Версия указана в свойствах `EW.DocHub.exe` (VersionInfo) и в имени файла
установщика. Единый источник — `APP_VERSION` в `main.py`: `EWDochub.spec`
читает её при сборке напрямую, `installer.iss` синхронизируется скриптом
`python tools/bump_version.py <X.Y.Z>`, согласованность проверяется smoke-тестом.

## Резервное копирование

* **Что копировать:** `%APPDATA%\DogovorGenerator` (реестр, настройки, ключ
  DaData, журнал) и папку документов (`Документы\EW.DocHub` по умолчанию).
* **Когда:** регулярно (например, раз в неделю) и обязательно перед
  обновлением или переносом на другой компьютер.
* **Как:** закройте программу (чтобы запись реестра завершилась) и скопируйте
  обе папки на другой носитель.
* **Проверка копии:** размер `database.db` больше нуля; в папке документов
  есть подпапки контрагентов; при включённой программе записи появляются
  после закрытия окна (транзакция завершена).

## Восстановление

* **Битая `database.db`.** Программа не затирает повреждённую базу: она
  сохраняет её как `database.db.bad-<метка>` и предупреждает при старте;
  запись транзакцией не оставляет «полусохранённых» версий — предыдущая
  версия данных гарантированно цела. Если база утеряна, а старый
  `database.json` остался — переименуйте его обратно в `database.json`:
  при следующем запуске он будет перенесён в новую базу.
* **«Предыдущие версии» Windows.** Правой кнопкой на `database.db` →
  «Восстановить прежнюю версию» — работает, если включена защита файлов
  Windows или есть точка восстановления.
* **Реестр утерян целиком.** При старте программа сверяет реестр с папкой
  документов: найденные «осиротевшие» файлы предлагается восстановить в
  реестр — тип, номер и дата берутся из имени файла, контрагент — по имени
  папки.
* **Повторный импорт** готовых документов восстанавливает записи, но
  теряется то, чего нет в исходных файлах: связи «доп. соглашение/спецификация
  → договор», позиции и суммы спецификаций, даты создания.
* **Перенос на другой ПК:** установить программу, закрыть её, скопировать
  `%APPDATA%\DogovorGenerator` и папку документов, запустить.

## Ограничения и известные проблемы

* Файлы не подписаны сертификатом — SmartScreen показывает предупреждение
  при первой установке.
* Импортированные документы открываются как исходные файлы; печатная форма
  пересобирается из шаблона только для документов, созданных в программе
  (у импортированных нет позиций/сумм в реестре).
* Правки документа в Word не синхронизируются с реестром: при «пересобрать
  из шаблона» документ будет воссоздан из данных реестра, а не из правок.
* Хранение — JSON: на очень больших реестрах (десятки тысяч записей) поиск
  и запись медленнее, чем могла бы быть с SQLite (перевод запланирован
  отдельным релизом).
* Автозаполнение по DaData работает только онлайн и ограничено тарифом
  (бесплатный — 10 000 запросов в день).
* Поиск в реестре фильтрует по названию и ИНН; по остальным полям (счёт,
  адрес, директор) поиска нет.
* Интерфейс тестировался на Windows 10/11 и в Linux (Xvfb); Win32-обвязка
  окна (скругление, «светофор») на других ОС деградирует в стандартную рамку.

## Безопасность и приватность

* При автозаполнении в DaData отправляется **только ИНН** (и тип
  организации): https://dadata.ru, данные юридических лиц/ИП из открытых
  реестров. ФИО, адреса, счета и тексты документов никуда не отправляются.
* Ключ DaData хранится локально (`%APPDATA%\DogovorGenerator\dadata_key.txt`),
  на Windows — зашифрованным через DPAPI (файл читают только процессы вашего
  пользователя; ключ из поля настроек не подставляется обратно), в коде и
  в репозитории секретов нет. Ключ — секрет пользователя: не передавайте
  его вместе с копиями реестра.
* Реестр и документы хранятся в открытом виде, шифрования нет — доступ
  определяется правами учётной записи Windows. Для чувствительных данных
  используйте шифрование диска (BitLocker) и стандартные ограничения доступа.
* Журнал (`logs/app.log`) фиксирует старт, ошибки и длительные операции;
  реквизиты (ИНН, счета, ФИО), названия и тексты документов в журнал не
  попадают.
* Импорт принимает только `.docx`/`.xlsx` с проверкой размеров и структуры
  ZIP («архивные бомбы» отклоняются); неопознанные файлы не открываются,
  а показываются «Показать в папке».

## Схема реестра (SQLite)

Источник правды — `%APPDATA%\DogovorGenerator\database.db` (SQLite,
WAL-журнал). Записи в памяти выглядят как раньше:

    контрагент: {"id", "type": "ooo"|"ip", "fields": {...}, "created_at"}
    документ:   {"id", "kind": ..., "party_id", "number", "date",
                 "data": {...}, "extra": {...}, "text", "created_at"}

В базе — три таблицы:

* `counterparties` — `id`, `type`, `fields` (JSON), `created_at`,
  `deleted_at`, колонка `inn` с индексом (поиск по ИНН);
* `documents` — `id`, `kind`, `party_id`, `number`, `date`, `data` (JSON),
  `extra` (JSON), `text`, `created_at`, `deleted_at`, `deleted_with_party`;
  индексы по контрагенту и типу документа;
* `meta` — `schema_version` и счётчик id (`seq`).

* `kind`: `contract` / `additional` / `spec` / `unknown`; непустой
  `deleted_at` — запись в корзине (автоочистка через 30 дней).
* **Перенос из JSON:** при первом запуске пустая база переносит старый
  `database.json` и сохраняет его как `database.json.migrated`; неизвестные
  поля сохраняются (колонка `extra_keys`). Повреждённая база →
  `.bad`-копия + предупреждение; запись транзакцией не теряет предыдущую
  версию данных.
* Ставки/реквизиты печатной формы спецификации (`settings.json`):
  `spec_supplier`, `spec_supplier_signatory`, `spec_city`, `spec_vat_rate`,
  `spec_appendix_number`, `spec_year`.

## Troubleshooting / FAQ

| Симптом | Что делать |
|---|---|
| DaData: «Неверный API-ключ» (401) | Проверьте ключ на dadata.ru; ключ задаётся в Настройках |
| DaData: «Превышен дневной лимит» (429) | Лимит бесплатного тарифа — ждите следующего дня или используйте платный |
| DaData: «Нет соединения» | Нужен интернет; без него всё остальное работает, кроме автозаполнения |
| DaData: «Ошибка сертификата (TLS)» | Проверьте системную дату и антивирус/прокси, перехватывающие трафик; корпоративный прокси требует установки своего корневого сертификата |
| Тост «…сохранён» без «и открыт» | Word/LibreOffice не установлен или нет ассоциации — «Показать в папке» |
| Пустой реестр при запуске | Читайте предупреждение при старте: повреждённая база убрана в `.bad` и реестр пуст, либо перенос из старого JSON не удался; проверьте папку данных |
| «Файл повреждён: это не корректный документ Office» при импорте | Файл не является валидным `.docx`/`.xlsx` — пересохраните |
| «.doc не поддерживаются» | Пересохраните документ в `.docx` |
| Импорт «тормозит» | Лимиты пакета: 200 файлов, 50 МБ на файл; загрузку можно отменить кнопкой «Отменить» |
| Второй экземпляр не открывается | Так задумано: активируется уже запущенное окно (защита реестра от перезаписи) |
| Файл «не открывается» без Word | Установите Word или LibreOffice; либо открывайте папку кнопкой «Показать в папке» |

## Надёжность и защита данных (с версии 1.4.0)

* **Блокировка второго экземпляра.** Одновременно может работать только одна
  копия программы: две копии писали бы в один файл реестра и теряли данные.
* **Атомарная запись реестра (v2.11.0 — SQLite).** Реестр записывается
  одной транзакцией в `database.db` (WAL, `synchronous=FULL`): либо весь
  реестр, либо ничего; сбой записи повторяется автоматически, предыдущая
  версия данных гарантированно цела.
* **Корзина.** Удаление переносит записи в корзину, файлы остаются;
  восстановление из раздела «Корзина»; записи старше 30 дней чистятся
  автоматически.
* **Подтверждения.** Ни одно удаление не выполняется без явного подтверждения
  с описанием последствий.
* **Сверка реестра и папки документов** при старте — реестр можно поднять
  из папки, если база утеряна.
* **Защита импорта:** лимиты размера/числа файлов, «архивные бомбы»
  отклоняются до разбора; причины отказа видны в отчёте.
* **Дубликаты:** карточка с существующим ИНН — только после явного выбора;
  повтор номера документа у контрагента требует подтверждения.
* **Несохранённые данные** не теряются молча: подтверждение при закрытии
  и уходе со страницы.
* **Журнал без реквизитов** — см. «Безопасность и приватность».

## Производительность (с версии 1.5.0)

* Шаблоны кэшируются; предпросмотр спецификации — с задержкой 120 мс;
  замена плейсхолдеров одним проходом; импорт пишет реестр одним
  сохранением; реестр не перерисовывается целиком; комбобокс и таблица
  позиций — без квадратичного торможения; операции дольше 500 мс
  фиксируются в журнале. Проверка производительности входит в
  `smoke_test.py` (600 контрагентов, 500 строк таблицы).

## Для разработчика

### Слои

| Модуль | Ответственность |
|---|---|
| `document_builder.py` | Печатные формы: поля `F`, плейсхолдеры `PH`, замены, НДС, прописью |
| `services.py` | Сервисный слой: валидация, кэш шаблонов, запись `.docx`, транзакция `save_document` (файл → запись → откат при сбое) |
| `storage.py` | JSON-хранилище: атомарная запись, копии, корзина, поиск |
| `document_importer.py` | Разбор импортируемых файлов (тип, реквизиты, номер, дата) |
| `dadata_client.py` | Автозаполнение по ИНН; ключ — только локально |
| `reconcile.py` | Сверка «реестр ↔ папка документов» |
| `applog.py`, `single_instance.py` | Журнал без реквизитов; блокировка второго экземпляра |
| `ui_macos.py`, `widgets.py`, `win_shell.py` | Примитивы интерфейса; `SpecTable`; Win32-обвязка окна |
| `main.py` | `ContractApp`: сбор форм, диалоги, отображение результата сервисов |

Направление зависимостей: `main → services → storage/document_builder`;
`document_importer → document_builder` (единый `F`). `services` и
`document_builder` интерфейса не знают — поэтому тесты идут без GUI.

### Как добавить поле в карточку

1. Добавьте ключ в `F` (`document_builder.py`) — имя поля меняется в одном
   месте.
2. Поле на форму — `main.py` (`_build_cp_fields`), валидация —
   `REQUIRED_*` / `validate_*` в `services.py`.
3. Если поле попадает в печатную форму — `PH` и `build_replacements`
   (`document_builder.py`) + плейсхолдер в шаблоне `.docx`.
4. Если поле приходит из импорта — регулярки в `document_importer.py`.
5. Прогоните `pytest tests/` и `python smoke_test.py`.

### Как добавить тип документа

`KIND_*` и `KIND_LABELS` в `storage.py` → `KIND_TO_PAGE` в `main.py` →
шаблон `.docx` + плейсхолдеры `PH` → `render_*` в `services.py` →
`build_record_docx` уже разрулит запись → страница в `ContractApp` →
`detect_kind` в импортере → golden-эталон (`tests/make_golden.py`).

### Как править печатную форму

Правка шаблона `.docx` → (при новых плейсхолдерах) `PH` +
`build_replacements` → перегенерация эталонов `python tests/make_golden.py`
→ `pytest tests/` покажет, если текст формы изменился нечаянно.

### Известные долги

* ~~SQLite вместо JSON~~ — сделано в v2.11.0: источник правды — база
  `database.db` (WAL, индекс по ИНН, транзакционная запись), старый JSON
  переносится при первом запуске.
* ~~Фасадный слой ContractApp~~ — удалён в v2.12.0: контроллеры вызываются
  напрямую (`app._doc_page_flow.*`, `app._lifecycle_flow.*`, …),
  `ContractApp` владеет только окном, навигацией, общим состоянием страниц
  и оболочкой (диалоги, тосты, статус).
* ~~Tk-тесты сборки виджетов~~ — добавлены в v2.12.0:
  `tests/test_tk_page_build.py` собирает приложение целиком под Xvfb
  (без дисплея модуль пропускается) и проверяет привязки трасс к методам
  контроллеров; покрытие `main.py` pytest-ом выросло до ~51 %.
* Живая пересборка интерфейса при смене DPI — не реализована (п. 6.3):
  при переносе окна на монитор с другим масштабом окно встаёт в
  подсказанный Windows прямоугольник, масштаб для новых диалогов
  пересчитывается (`ContractApp._on_dpichanged`, v2.13.0), но уже
  построенные страницы не пересобираются — их размеры фиксированы на
  момент сборки. Заметно только при перетаскивании окна между мониторами
  с разным масштабом во время работы; после перезапуска интерфейс
  собирается уже под новый масштаб.
