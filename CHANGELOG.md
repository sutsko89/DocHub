## 2.25.2 — 2026-11-23 (замеры раздела Е на целевой Windows: STORE-1A и TREE-1 подтверждены)

Прогоны выполнены пользователем по протоколу
`docs/protocol-section-e.md` (v2.25.1) на целевой Windows (Python 3.13,
детерминированные наборы generate_registry; stdout прогонов приложен).
Продуктовый код не меняется — фиксируются подтверждённые цифры и решения.

* E-1 STORE-1A — подтверждено. Набор «10k» фактически 11 999 записей
  (2000 контрагентов + 9999 документов), «50k» — 59 999. Медианы по 5
  повторам: точечная правка + save() — 14,2 мс @12k (порог аудита
  ≤ 15 мс выполнен; дисперсия повторов 12,3–82,7 мс — фоновые помехи
  машины, медиана устойчива) и 30,4 мс @60k; save() без изменений —
  0,12 / 0,21 мс (запись не выполняется, ревизия не растёт — R-01);
  счётчики статусной строки — 2,5 мс @12k / 13,4 мс @60k. Полная
  перезапись save_full() (= «до»-значение по протоколу) — 1,4 с @12k и
  ~16 с @60k: инкрементальная запись быстрее полного пути в ~99–526 раз.
  Пометки «не проверено» для STORE-1A в 2.24.0 закрыты этим прогоном.
* E-3 TREE-1 — подтверждено на 1k/50k. Арми «до»: популяция строк
  CTk-виджетов 5,19 с cold / 5,02 с warm @1k — оценка П-аудита P-02
  «10k — минуты» подтверждается. Арм Treeview («после»): популяция
  7,6 мс @1k / 413 мс @50k, тик прокрутки ≤ 0,06 мс (порог 50 мс),
  item() на 1000 строк — 6–8 мс, вставка/удаление 100 строк — 0,7 мс.
  Формальный порог 300 мс @10k не снят (прогон e3-10k не выполнялся);
  интерполяция по 1k/50k даёт ~90 мс — оценка, а не замер. select_200
  @50k — 381 мс (1,9 мс на операцию: каждый selection_set в замере
  перерисовывает выделение; в UI клик — одна операция).
* E-2 PERF-2 — не снято: сеанс жестов с EWDOCHUB_PERF_LOG не
  выполнялся, порог p95 dt тика pointer.poller ≤ 25 мс остаётся
  «не проверено».
* Решение по STORE-1B (условная карточка «фоновый single-writer»):
  точечная запись 14–30 мс на целевой машине — UI-бюджет выполняется
  без вынесения записи из потока; карточка закрыта решением «не требуется»,
  основание — замеры раздела Е.

## 2.25.0 — 2026-11-23 (этап 4 roadmap «Реестр на Treeview и UX реестра»: TREE-1 + UX-REG)

Реализация этапа 4 объединённого roadmap rev2 одной волной (коммит-база —
этап 3, APP_VERSION 2.24.0): UX реестра реализован на новом виджете сразу,
чтобы не перерисовывать строки дважды. Схема базы и сценарии данных не
меняются; имена состояния страницы сохранены (`registry_list`,
`_registry_rows`, `_docs_rows`, `_registry_selected_id`, `_docs_selected_id`,
`_registry_drill_party_id`, `_registry_rendered`). Прототип-замер и решение
R-05b — `tools/bench_tree_prototype.py` (детерминированные наборы, тот же
инструмент годится для «до/после» на Windows по разделу Е). Черновые
замеры ниже — Linux/Xvfb, синтетика; подтверждение на целевой Windows —
«не проверено» до прогона раздела Е.

### TREE-1 — реестр на ttk.Treeview: точечные обновления и панель действий

* R-03: список реестра — один ttk.Treeview вместо пересоздания ~10
  CTk-виджетов на строку (П-аудит P-02: 8–9 мс/строка, 10k — минуты).
  Стилизация под светлую/тёмную тему через ttk.Style (фон карточки, шапка
  chrome, скроллбар палитры), слушатель темы снимается вместе с виджетом
  (LEAK-1); теги сроков «expired»/«soon» красят строки документов теми же
  цветами, что были у CTk-строк (2.18.0).
* R-04: карта id→iid и точечные обновления дифом. Полная популяция —
  только при смене фильтра/сортировки/фильтра типов и drill-переходах
  (сигнатура вида); добавление, удаление, правка, восстановление и импорт
  идут дифом: неизменный префикс строк не трогается (iid сохраняются —
  критерий 5.1), правится только суффикс после первой расходимости.
  Контрольный assert в debug-сборке: порядок дерева совпадает с моделью.
* Панель действий выделенной записи под списком (V3 «резерв места»):
  контрагент — «Редактировать»/«Удалить», документ — «Открыть Word»/
  «Удалить», корзина — «Восстановить»/«Удалить навсегда», неопознанные —
  «Показать в папке»/«Удалить»; «Очистить корзину» — на той же панели.
  Кнопки в каждой строке удалены; высота панели постоянна. Delete на
  выделенной записи корзины не действует — там выбор restore/purge,
  случайное удаление навсегда недопустимо.
* R-05b (лимит отображения — решение по замеру, не константа): мягкий
  лимит 10 000 строк. Прототип: популяция 10k — 86 мс при пороге раздела
  Е 300 мс (запас 3,5×), прокрутка — нативная, максимальный тик 0,06 мс
  при пороге 50 мс; 50k — 447 мс, поэтому объёмы больше лимита
  показываются порциями с «Показать ещё (+10 000)» и подписью «показаны
  все N» в конце. Поиск и сортировка всегда по всей базе — контракт
  независимо от лимита: запись № 10 000 на наборе 10 000 доступна напрямую,
  поиск находит запись № 5 000 независимо от видимой порции; после
  «Показать ещё» фильтр, сортировка, выделение и позиция сохраняются.
* Черновой замер виджета (Linux/Xvfb, синтетика): популяция 8,6 мс @1k /
  86 мс @10k / 447 мс @50k; диф-операции (правка/вставка/удаление одной
  записи) 1,5–1,7 мс @1k, 16–17 мс @10k, 86–96 мс @50k; построение модели
  строк 26 мс @10k. Прежний путь (строки CTk) на тех же данных —
  8,5 мс/строку @1k (прогон этого релиза), 17,2 с @10k (замер DIAG-1).
  Подтверждение «до/после» на Windows — по разделу Е («не проверено»).
* Секции «Неопознанные документы» и «Корзина» переехали в дерево
  (заголовки-строки секции + строки записей с действиями через панель),
  баннеры сроков и файлов вне реестра остались компактными фреймами над
  списком. perf-метр DIAG-1 привязан к новому списку (тики раскладок —
  `<Configure>` дерева; «registry.canvas» — имя источника сохранено).

## 2.24.0 — 2026-11-21 (этап 3 roadmap «Инкрементальная запись базы»: STORE-1A)

Реализация этапа 3 объединённого roadmap rev2 (коммит-база — параллельные
ветки этапа 2, APP_VERSION 2.23.0). Схема базы НЕ меняется: строки
сохраняются в те же таблицы и колонки (включая overflow в extra_keys),
schema_version остаётся 1 — база, записанная инкрементально, читается
прошлой версией кода без миграции, а полная перезапись старой версии
поверх остаётся допустимой. STORE-1B (фоновый single-writer) — условная
задача: решается повторным замером по разделу Е после STORE-1A; ослабление
synchronous=FULL запрещено карточкой и не выполнялось.

### STORE-1A — инкрементальная запись базы и счётчики статусной строки (R-01 + R-05a)

* R-01: dirty-наборы в DataStore. Мутаторы (add/update/trash/restore/
  purge/cleanup/delete) помечают id изменённых и изъятых записей; save()
  пишет только dirty-строки (INSERT OR REPLACE по изменённым id) и удаляет
  изъятые (DELETE) — одной транзакцией «либо всё, либо ничего». При
  отсутствии изменений запись не выполняется вовсе: ревизия не растёт,
  автокопия BKUP-1 не запускается.
* Dirty-наборы очищаются только после подтверждения транзакции: сбой
  записи не теряет изменения, повторный save() их дописывает, last_error
  доходит до UI. Запись, снятая из памяти при сбое сохранения
  (services.save_document, DEF-4), превращается в DELETE — точечная
  запись не воскресает строку.
* seq в meta обновляется при добавлении записи, rev — каждой успешной
  записью (триггер автокопий BKUP-1); прочие ключи meta не трогаются.
* Полный путь остаётся: save_full() перезаписывает все строки — откат и
  самопроверка, перенос старого JSON. Миграция имён полей v2.13.0 при
  загрузке помечает нормализованные записи dirty — старый ключ уходит
  с диска следующей save() без полной перезаписи. Публичный mark_dirty —
  для редких правок мимо мутаторов.
* R-05a: счётчики статусной строки — тремя COUNT(*) index-only сканом
  по idx_counterparties_deleted и новому покрывающему индексу
  idx_documents_status(deleted_at, kind); main._update_status больше не
  строит списки активных записей в памяти (П-аудит P-10). При недоступной
  базе — честный откат к подсчёту по памяти, статусная строка не пустеет.
* Черновой замер (Linux-песочница, синтетика): полная перезапись 145 мс
  @10k — точечная правка 2.9 мс; @50k — 660 мс против 14.5 мс. Цель
  аудита ≤ 15 мс UI-времени @10k выполняется с запасом; подтверждение —
  замер «до/после» по разделу Е на целевой машине Windows (в песочнице
  недоступно, помечено «не проверено»). status_counts: 1.3 мс @10k
  (было 4.1 мс по памяти), 4.4 мс @50k (было 25.4 мс).
* Тесты: +15 (test_storage_incremental.py): no-op save без записи;
  точечная правка без вызова полного пути; фантом→DELETE; критерий
  карточки «500 случайных операций (add/edit/trash/restore/purge), после
  каждой дамп базы сравнивается с памятью»; сбой записи сохраняет dirty
  и last_error; форма схемы не изменилась; status_counts == памяти
  (включая KIND_UNKNOWN и корзину) с откатом при недоступной базе; план
  COUNT(*) идёт по покрывающему индексу; операции реестра видны в
  perf-канале (EWDOCHUB_PERF_LOG, критерий «не прерывают dt тики пулера»
  проверяется замером по разделу Е); грубая граница времени точечной
  save(). Smoke 2.1 и два теста сбоя обновлены под инкрементальный
  контракт (ретраи проверяются с pending-изменением save=False).

## 2.23.0 — 2026-11-21 (этап 2 roadmap, параллельные ветки: UX-A «Дешёвая UX-ветка форм» + HYG-1 «Гигиена поставки»)

Реализация параллельных веток этапа 2, не вошедших в 2.22.0 (коммит-база —
этап 2, APP_VERSION 2.22.0). UX-A ведётся в своих модулях (ui_macos,
counterparty_controller, document_page_controller, document_save_controller,
main, settings_controller) и не пересекается с оконным слоем PERF-2;
HYG-1 — только CI и лицензия. По карточке UX-A риски из roadmap закрыты
конструкцией: подсказка формата — подложка, а не значение поля; деструктивные
подтверждения (удаление, очистка, потеря правок, установка обновления) не
переведены на «Enter = ОК» — флаг destructive=True у каждого из них
закреплён AST-тестом.

### UX-A — дешёвая UX-ветка форм (UX-аудит U3-U7, U14, V1)

* V1: контраст пар палитры проверяется автоматически — `contrast_ratio`
  (формула WCAG 2.x), `CONTRAST_BASELINE` из 14 пар «текст — фон» для обеих
  тем и тест-гейт `contrast_baseline_violations() == []`. Третичный текст
  светлой темы #96969C — значение, подтверждённое UX-аудитом, зафиксировано
  тестом.
* U3: блок «Поиск по ИНН» (готовый блок страницы «Договор») вынесен
  в `build_party_search_row` и включён на страницах «Доп. соглашение»
  и «Спецификация»: найденный контрагент подставляется сразу во все
  страницы через `set_current_party`; прежнее имя `contract_search_var`
  сохранено (smoke-тест и страницы).
* U4: подсказки формата в полях с жёстким форматом (ИНН «10 или 12 цифр»,
  КПП «9 цифр», ОГРН «13 цифр», ОГРНИП «15 цифр», р/с и к/с «20 цифр»,
  БИК «9 цифр») — в пустом ненаходящемся в фокусе поле, и в карточке на
  странице, и в окне редактирования. Подсказка — надпись-подложка
  (`TextField.set_placeholder`), а не содержимое Entry: `get()` пустого
  поля всегда возвращает пустую строку, подсказка физически не может
  попасть в карточку или документ.
* U5: прокрутка к ошибочному полю — `scroll_to_widget` /
  `containing_scroller` вызываются после подсветки ошибок валидации
  (страница карточки и окно редактирования): поле больше не остаётся

## 2.20.0 — 2026-11-20 (функция: прилипание окна к краям монитора; плавный перенос и растягивание)

Отзыв пользователя на 2.19.3: «перетаскивание работает, на второй монитор
уносится, программа не вылетает. Но не работает разворачивание окна
перетаскиванием в верхнюю границу экрана… Все манипуляции с окном
проходят дергано, разворачивание происходит какими-то квадратами».

### Причина дёрганости и «квадратов»

* Ручной перенос (единственный после 2.19.3) двигал окно из обработчика
  `<B1-Motion>`. Tk на Windows при захвате указателя доставляет эти
  события рвано — пачками и с внутренними паузами (внутренний таймер
  опроса указателя), поэтому окно отставало от курсора и догоняло его
  скачками: «дергано… какими-то квадратами».
* Разворачивание перетаскиванием было невозможно в принципе: Aero Snap
  активируется только нативным циклом Windows, который в 2.19.3 удалён
  как причина вылетов без traceback (пустой crash.log). Возвращать его
  нельзя — стабильность важнее.

### Прилипание — без нативных циклов (безопасная эмуляция)

* Зоны прилипания считаются вручную (`ui.snap_zone` — чистая функция):
  кромки ОКНА сравниваются с краями рабочей области ТОГО монитора, под
  которым курсор (`win_shell.workarea_at` через MonitorFromPoint) —
  прилипание работает у края любого монитора, включая второй. Верхняя
  граница — разворачивание, левый/правый край — половина области; углы
  дают половину по горизонтали (стиль Windows 10). Полоса зоны —
  ±16 логических px (`ui.SNAP_EDGE`), масштабируется с интерфейсом;
  окно, вдвинутое за край дальше полосы, зону снимает — перенос на
  соседний монитор не перехватывается.
* Пока окно держит зону, показывается полупрозрачная подложка
  (`ui.SnapPreview`): цвет акцента темы, alpha 0.25, поверх всех; на
  средах без альфы рисуется сплошным цветом. Прилипание применяется
  при отпускании кнопки (`main.ContractApp._snap_apply`): прежняя
  геометрия запоминается в `_restore_geometry` — двойной клик, кнопка
  «развернуть» и перетаскивание шапки возвращают окно к прежнему
  размеру (как в Windows). В полноэкранном режиме F11 прилипание не
  применяется. Половина экрана уже минимума окна — зажим в минимальный
  размер (контракт закреплён smoke-проверкой).
* Никаких нативных циклов и подмен WndProc сверх существующего хука
  WM_DROPFILES/WM_DPICHANGED: тот лежит вне модальных циклов и работал
  во всех версиях — риск повторения вылетов 2.17.0/2.19.1 исключён.

### Плавность: опрос курсора с постоянным темпом

* `ui.PointerPoller`: на время переноса/растягивания позиция курсора
  опрашивается каждые ~16 мс (`winfo_pointerx/y` — прямой опрос ОС мимо
  очереди событий) и окно двигается ровными шагами ~60 Гц; `<B1-Motion>`
  остаётся для мгновенной реакции, оба пути сходятся в один шаг.
  Одинаковая позиция не порождает лишних `geometry()`. Пулер сам
  гасится при сбое callback, разрушении окна и отпускании кнопки
  (`ButtonRelease` теперь привязан и к кромкам растягивания).
* Растягивание за кромки переведено на тот же пулер (кромка тянется по
  актуальной позиции курсора), состояние растягивания сбрасывается при

## 2.19.3 — 2026-11-20 (исправление: вылет при перетаскивании — нативный цикл удалён полностью)

Отзыв пользователя на 2.19.1: «crash.log пустой. Баг с вылетом при
перетаскивании остался» (с приложенным app.log).

### Диагностика по логам пользователя

* faulthandler включён (в app.log строка «Дамп критических сбоев
  включён: …\logs\crash.log»), но **crash.log пуст** — процесс умирает
  путём, который faulthandler записать не может: быстрый фейл

  диспетчеризует SEH, дамп не пишется. Это повреждение native-памяти
  Tcl/Tk, а не Python-исключение.
* В app.log несколько сеансов заканчиваются БЕЗ строки «Приложение
  закрыто пользователем» (14:26:08 → рестарт через 12 секунд;
  15:52:09; 16:10:10) — жёсткие смерти. Все такие смерти — только в

  с ручным переносом через `geometry()` завершаются штатно.
* Вывод: убивать процесс может только нативный модальный цикл
  `SendMessageW(WM_NCLBUTTONDOWN)`. «Отложенный» старт 2.19.1 не

  цикла всё равно перекачивает WM_MOUSEMOVE/WM_PAINT/WM_DPICHANGED
  через Tk-обработчики — ре-entrant обработка событий Tcl из вложенного

* Нативный перенос и растягивание удалены полностью (`win_shell`):

  глушитель `EWDOCHUB_NO_NATIVE_DRAG` — всё убрано вместе с функциями

* Второй монитор возвращён ручному переносу без нативных вызовов:

  Окно уносится на любой монитор (в т. ч. слева и сверху), но не
  теряется за краями: у границы остаётся полоса 48 px

  прячется выше верхнего монитора. Смена DPI при переносе между
  мониторами по-прежнему обрабатывается хуком WM_DPICHANGED.
* Aero Snap недоступен (нужен именно нативный цикл) — осознанный
  компромисс: стабильность важнее прилипания. Двойной клик —

* Хуки окна (WM_DROPFILES — drag-and-drop файлов, WM_DPICHANGED)

  версиях.

## 2.19.2 — 2026-11-20 (исправление: зависание скачивания обновления; галочка «Запустить»)

Запрос пользователя: «Скачивание обновления не работает. 0,0мб из 19,5мб
висит уже минуту. Подключение к интернету есть. В инсталлер добавить
галочку "запустить"».

### Причина зависания

Окно скачивания обновления застывало на «0,0 МБ из 19,5 МБ» навсегда:
`download_tick` после обработки первого же события ``progress`` возвращался,
**не перевесив** `after(80, …)` — цикл опроса очереди умирал. Скачивание
в рабочем потоке продолжалось (порции писались в файл, события прогресса
копились в очереди), но интерфейс их больше не забирал: полоса не двигалась,
а финальное ``done`` оставалось в очереди — до диалога установки дело не
доходило. Тесты этого не видели, потому что скармливали тику только
терминальные события (``done``/``error``), для которых остановка цикла
законна.

### Исправление

* `updater_controller.download_tick` переписан на осушающий цикл: за один
  тик очередь разбирается пачкой (прогресс не отстаёт от скачивания),
  после каждого не-терминального события (``progress``, ``phase``)
  ``after`` перевешивается гарантированно; остановка — только на
  ``done``/``cancelled``/``error``.
* Попутно: событие ``phase`` («Проверка целостности файла…») больше не
  разрушает окно прогресса — раньше окно закрывалось до диалога
  подтверждения, и фаза проверки не была видна пользователю; теперь
  меняется только строка статуса (`_set_download_status`).
* Сеть не менялась: `urllib` с таймаутом сокета 30 с, потоковая запись
  в `.part`, SHA-256 по `SHA256SUMS.txt` — как в 2.18.0.

### Инсталлер: галочка «Запустить»

* `installer.iss` `[Run]`: запись имела флаг `skipifnotsilent` и потому
  срабатывала только в тихой установке — при обычной установке чекбокс
  «Запустить EW.DocHub» на странице «Завершение» не показывался вовсе.
  Теперь две записи: чекбокс «Запустить EW.DocHub» для интерактивной
  установки (`postinstall skipifsilent`, по умолчанию включён) и
  безусловный автозапуск после тихого обновления (`skipifnotsilent`) —
  автообновление 2.18.0 по-прежнему перезапускает приложение само.

### Тесты

* pytest 578 (+5): `download_tick` — событие прогресса продолжает цикл
  опроса, прогресс обновляет полосу и статус, фаза проверки сохраняет
  окно, пачка progress+phase+done осушается до подтверждения установки,
  отмена/ошибка останавливают опрос без диалогов.
* smoke 341 (+2): рабочий поток отчитывается событиями прогресса; тик с

* Проверено: pytest — 578 passed / 0 failed / 0 skipped (Xvfb),
  smoke_test — 341 проверка.

## 2.19.1 — 2026-11-20 (исправление: вылет при перетаскивании окна)

Запрос пользователя: «При перетаскивании окна, программа вылетает. Это
очень серьзный БАГ».

### Причина

Нативное перетаскивание (2.17.0) запускало `SendMessageW(WM_NCLBUTTONDOWN,
HTCAPTION)` прямо изнутри Tk-обработчика нажатия шапки (и кромок
растягивания). Вызов блокирует до отпускания кнопки мыши: Windows
раскручивает вложенный модальный message loop поверх незавершённого
колбэка ButtonPress, и все сообщения окна (WM_MOUSEMOVE, WM_PAINT,
WM_DPICHANGED, …) перекачиваются через Tk-обработчики ре-entrantly —
события Tcl обрабатываются внутри не завершившегося стека. На Windows
это заканчивалось падением процесса без traceback («программа вылетает»).

### Исправление

* `win_shell`: новые `begin_native_move_deferred` /
  `begin_native_resize_deferred` — модальный цикл стартует из
  `after_idle`, когда стек Tk полностью раскрутился (как в окне с
  системной рамкой). Перед стартом проверяются `winfo_exists()` и
  `GetAsyncKeyState(VK_LBUTTON)`: клик без движения в цикл переноса не
  входит. Второй монитор (со сменой DPI) и Aero Snap работают как прежде.
* `WindowDrag._press` и `ContractApp._resize_press` переведены на
  отложенный вариант; ручной путь (`geometry()`) остался для не-Windows
  и как страховка при сбое Win32-вызова.
* Глушитель `EWDOCHUB_NO_NATIVE_DRAG=1`: при его задании перетаскивание
  и растягивание идут ручным Tk-путём (без Snap/второго монитора) —
  для диагностики проблем с оконным циклом на конкретных машинах.
* Диагностика хард-падений: `applog.enable_crash_dump()` включает
  `faulthandler` — фатальные сбои Tcl/Tk теперь пишут C-стек и цепочку
  вызовов Python в `%APPDATA%\DogovorGenerator\logs\crash.log` (раньше
  процесс умирал молча, и точка падения была неизвестна).
* `_main_hwnd`: `GetParent` объявлен с 64-битным `restype` — HWND больше
  не усекается до `c_int`.
* Тесты: +19 (контракты отложенного переноса — планирование в after_idle,
  страж кнопки мыши, глушитель env, тиша на мёртвом окне; диспетчеризация
  WindowDrag — нативный путь не выполняет блокирующей работы в колбэке,
  ручной fallback двигает окно и зажимает позиции; интеграционные —
  перетаскивание шапки на живом окне). Итого 573 pytest + 339 smoke.

## 2.17.0 — 2026-11-20 (окно: нативное перетаскивание на второй монитор и Aero Snap)

Критический отзыв пользователя: окно нельзя было перетащить на второй
монитор, не работал Snap (разворачивание перетаскиванием к краям).

### Причина
* Окно безрамочное (`win_shell.make_borderless` → `overrideredirect`),
  перенос делался вручную через `geometry()` с зажимами `x ≥ −40`,
  `y ≥ 0` — на монитор слева/сверху окно утащить было невозможно в
  принципе, а Windows при ручном переносе не видит «перетаскивание за
  заголовок»: Aero Snap недоступен. Ручное растягивание за кромки к тому
  же зажималось рабочей областью основного монитора (`workarea()` без
  аргумента).

### Исправление
* `win_shell.begin_native_move` / `begin_native_resize` (2.17.0):
  перенос и растягивание отдаются самой Windows через синтетический
  `WM_NCLBUTTONDOWN` с HT-кодом точки (HTCAPTION / HT* восьми кромок).
  Windows ведёт нативный модальный цикл: окно уносится на второй монитор
  (со штатной обработкой смены DPI через `WM_DPICHANGED`), работает
  Aero Snap прилипанием к краям и верхней кромке.
* `make_borderless` добавляет окну стилевые биты WS_MAXIMIZEBOX /
  WS_MINIMIZEBOX / WS_SYSMENU (визуального следа нет) + SetWindowPos
  FRAMECHANGED: без них Snap считает окно неразворачиваемым.
* `ui.WindowDrag._press`: сначала нативный перенос, ручной путь сохранён
  как fallback (не-Windows, сбой Win32-вызова). Поведение «тянешь
  развёрнутое окно — восстанавливается под курсором» сохранено
  (`on_start` срабатывает до запуска нативного цикла).
* Растягивание за 8 кромок (`main._resize_press`): нативный цикл вместо
  ручного; fallback учитывает рабочую область того монитора, где окно
  (`workarea(self.root)`).
* Тесты: HT-мапа всех восьми кромок и системные константы; не-Windows
  ветки `begin_native_move`/`begin_native_resize` возвращают False

## 2.11.0 — 2026-11-19 (SQLite вместо JSON)

Пункт 11 этапа 5 плана — источник правды реестра переведён с JSON-файла
на SQLite-базу (`database.db`). API `DataStore` не изменился ни на один
метод: в памяти — те же два списка словарей, все контроллеры, тесты и
smoke-подмены работают как раньше. Полный pytest 417 → 422 зелёный.

### Архитектура
* **База `database.db` вместо `database.json`** (storage.py переписан,
  публичный API и поведение методов сохранены 1-в-1):
  - WAL-журнал (`PRAGMA journal_mode=WAL`) — чтение не блокирует запись,
    второй экземпляр программы безопасно работает параллельно;
    `busy_timeout=5 c` вместо мгновенного сбоя при занятой базе.
  - `synchronous=FULL` — коммит доходит до диска до подтверждения
    (замена fsync у старых `.bak`-копий, гарантия сбоя питания).
  - Запись — одна транзакция на весь реестр: либо всё, либо ничего;
    при сбое предыдущая версия базы не теряется, `last_error` заполняется
    как раньше (до 3 попыток при временных сбоях — антивирус, индексатор).
  - Сериализация до открытия базы: битые данные не роняют файл.
* **Индексы.** `counterparties.inn` — отдельная колонка с индексом
  `idx_counterparties_inn` (поиск по ИНН из DaData-поиска); индексы
  документов по контрагенту и типу (`idx_documents_party`,
  `idx_documents_kind`) и по корзине (`idx_*_deleted`).
* **Миграция JSON → SQLite.** При первом запуске пустая база читает старый
  `database.json` (те же проверки структуры, что раньше) и переносит записи;
  перенесённый файл сохраняется как `database.json.migrated`. Повторный
  перенос невозможен (триггер — пустая база без метки `meta.seq`). Битый
  legacy-JSON не трогается — это единственная копия данных, пользователь
  предупреждается. Дубли id при переносе схлопываются (база не допустит
  второй записи с тем же PRIMARY KEY), счётчик id продолжается.
* **Схема без потерь.** Ключи записи, у которых нет собственной колонки
  (запас на будущее), сохраняются в `extra_keys` как JSON и восстанавливаются
  при чтении — перенос в обе стороны не теряет ни одного ключа.
* **Повреждённая база** (не SQLite-файл / «disk image is malformed») —
  убирается в `database.db.bad-<метка>` (вместе с `-wal`/`-shm`), реестр
  начинается с пустой базы, предупреждение показывается как раньше; старые
  `.bad`-копии (включая `database.json.bad-*` прежних версий) чистятся
  по возрасту, как и было (аудит 2.0.1).
* **Ушло с JSON-бэкендом:** ротация `.bak.1…4`, черновики
  `database.json.<pid>.tmp`, восстановление из `.tmp` — их роль взяли на
  себя транзакции и WAL.
