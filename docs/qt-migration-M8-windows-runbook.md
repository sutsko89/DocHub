# EW.DocHub — Windows-runbook этапа M8: публикация релиза 2.29.0, откат

Linux-часть M8 выполнена (см. `qt-migration-M8-report.md`). Этот runbook —
публикация релиза и приёмка на Windows (Windows 10/11 x64). Каждый шаг
фиксирует результат в протокол; «не проверено» снимается только фактом
прогона.

Рабочее состояние: `main` содержит код миграции M0–M7 + релизный коммит
2.29.0 (`app_common.APP_VERSION = "2.29.0"`) — ПОСЛЕ выполнения шага 0.
Профили для прогонов — изолированные (И.1):
`$env:APPDATA = "C:\bench\profile"`. Реальную машину для К-5 обновлять
только после чек-листа И.1 (закрыта Tk-сессия, есть копия профиля,
кросс-тест зелёный).

## Шаг 0. Пуш кода из релизного bundle (мобильный/стационарный ПК с git, ~5 минут)

Песочница не может передать код через плагин (inline-only) и не имеет
учётных данных для git push. Каноническая история M3–M7 + релиз
упакована в bundle `DocHub-qt-migration-release-M8.bundle`. ВЕРШИНА
ветки — merge-коммит публикации: он соединяет линию GitHub
`qt-migration` (084b9b3, M0–M2+снимок M6-документации) с канонической
историей (релизный коммит 2.29.0); ДЕРЕВО merge-коммита == дереву
релизного коммита (стратегия `ours` — релизное, проверено хешем
дерева), обе линии сохранены в предках — никакие коммиты не теряются.

```bash
# 1. Клон из bundle (полная история)
git clone DocHub-qt-migration-release-M8.bundle dochub-push
cd dochub-push
git checkout qt-migration

# 2. GitHub как remote
git remote add gh https://github.com/sutsko89/DocHub.git
git fetch gh

# 3. Пуши — ОБА fast-forward (вершина содержит и 084b9b3, и 52d96eb;
#    force не нужен, история GitHub не переписывается)
git push gh qt-migration           # FF: 084b9b3 → вершина
git push gh qt-migration:main      # FF: main 52d96eb → вершина
```

Проверка после пуша: на GitHub в `main` — README «(версия 2.29.0)»,
CHANGELOG с записью 2.29.0, файлы `updater_qt.py`, `installer_qt.iss`,
`docs/qt-migration-M8-report.md`; коммит `qt-migration` — merge с
двумя родителями (линия GitHub + каноническая линия).

## Шаг 1. Публикация релиза (браузер, ~5 минут + время CI)

1. GitHub → **Releases → Draft a new release**.
2. **Choose a tag** → ввести `v2.29.0` → «Create new tag on publish»,
   Target: `main` (должен содержать релизный коммит 2.29.0).
3. Title: `EW.DocHub v2.29.0`. Body: можно пусто — CI перезапишет своим
   текстом; после прогона вставить текст из
   `docs/RELEASE_NOTES_v2.29.0.md`.
4. **Publish release** — пуш тега запускает `release.yml`:
   pytest + smoke Tk + smoke Qt на windows-latest → PyInstaller обоих
   флейворов → Inno Setup обоих установщиков → подпись (если секреты
   заданы) → `SHA256SUMS.txt` → GitHub Release.

Фиксировать в протокол: ссылка на прогон Actions (зелёный), время,
наличие ассетов: `EW.DocHub-2.29.0-qt-setup.exe`,
`EW.DocHub-2.29.0-setup.exe`, `SHA256SUMS.txt` с ДВУМЯ строками;
имя Qt-ассета оканчивается на `-qt-setup.exe` (контракт флейвор-выбора).

Если CI упал — разбирать по логу шага (pytest/smoke на Windows первым
делом: новая платформа = новые отказы; правило Е §9 — доклад с логами
как есть).

## Шаг 2. Обновление Tk 2.28.2 → Qt 2.29.0 (К-5, критерий M8)

1. Взять машину с установленной Tk-сборкой 2.28.2 (или установить
   `EW.DocHub-2.28.2-setup.exe` с релиза v2.20.0… — если на машине
   нет 2.28.2, сначала поставить её из ассета релиза, содержащего
   Tk-установщик; для чистоты эксперимента — на копии профиля).
2. Запустить EW.DocHub (Tk) — реестр/настройки/ключ на месте. Создать
   контрольного контрагента и договор.
3. Запустить `EW.DocHub-2.29.0-qt-setup.exe` поверх (не снося 2.28.2).
   Ожидание: установщик ставит Qt-сборку в ТУ ЖЕ папку (один AppId),
   `[InstallDelete]` чистит старые файлы сборки, данные `%APPDATA%`
   не трогает.
4. Запустить приложение: окно Qt с системной рамкой; **реестр,
   настройки (тема/папка/константы), ключ DaData, контрольный
   контрагент и договор — на месте**; сборка «Настройки → Обновления»:
   версия «2.29.0-qt».
5. Открыть договор — печатная форма собирается (шаблоны те же).
6. Фиксировать: SmartScreen-поведение, AppMutex-конфликт при запущенной
   программе (установщик просит закрыть), DPI 150 % — размер интерфейса.

## Шаг 3. Канал обновлений Qt (санити до К-6)

* «Настройки → Обновления» → «Проверить обновления»: релиз v2.29.0 —
  собственная версия; приложение не предлагает обновиться само на себя
  (сравнение по числовой части: 2.29.0 = 2.29.0).
* Ассет чужого флейвора не скачивается: unit-тесты
  `test_installer_asset_for_flavor_never_returns_foreign` +
  smoke Г #17 уже зелёные; на Windows подтверждается в К-6.

## Шаг 4. Откат на 2.28.2 (И.3, критерий M8)

1. Скачать с релиза-страницы `EW.DocHub-2.28.2-setup.exe` (ассет
   предыдущей линии) и установить поверх Qt 2.29.0.
2. Запустить: Tk-интерфейс, данные профиля на месте (реестр читает
   базу после Qt-сессии — контракт «база после Qt читается Tk»).
3. Вернуть Qt: `EW.DocHub-2.29.0-qt-setup.exe` поверх.
4. Фиксировать: обе перестановки без потери данных.

## Шаг 5. Замеры раздела Е (цифры → CHANGELOG 2.29.0)

Изолированный профиль `C:\bench\profile`, синтетика
`tools/generate_registry.py` (никогда на реальной базе). Протокол —
раздел Е плана; фиксировать: старт до окна/до готовности, память @10k,
вставка 500 строк, реестр @10k, P-08 (bench_docx_build). Результаты
внести в раздел «Не проверено» записи 2.29.0 CHANGELOG.md (строка
«Замеры раздела Е … цифры вносятся») коммитом «docs: замеры Е 2.29.0».

## Шаг 6. К-8: сетевая папка документов

Папка документов на сетевом ресурсе (Настройки → папка): сохранение,
экспорт, открытие, свёрка сирот. Фиксировать задержки и ошибки записи
(честные сообщения).

## Шаг 7. К-6 — после СЛЕДУЮЩЕГО релиза (Qt→Qt)

Полная цепочка (автопроверка → скачивание ассета своего флейвора →
SHA-256 → тихая установка → перезапуск новой версией) проверяется между
двумя фактическими Qt-релизами (И.2). Пункт CP2/M8 остаётся «не
проверено» до этого прогона — по плану это допускается явно.
