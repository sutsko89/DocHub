# История версий EW.DocHub

Все изменения описаны относительно пунктов «Плана_исправлений.md».

## 2.6.0 — 2026-11-19 (декомпозиция: шаг 5)

Пятый шаг плана P2 из аудита 2.0.1 («по одному контроллеру за
итерацию»): страница «Спецификация» и сценарии сохранения договора,
доп. соглашения и спецификации вынесены в DocumentSaveController.
Поведение приложения не менялось: полный pytest 256 → 302 и smoke
306/306 зелёные.

### Архитектура
* **document_save_controller.py — DocumentSaveController (P2).** Кластер
  сохранения переехал из main.py целиком: сборка страницы «Спецификация»
  (таблица позиций, контрагент, договор-основание, условия поставки),
  подстановка договора при выборе контрагента (п. 5.1), отложенный
  предпросмотр спецификации (п. 5.6), подтверждение повтора номера
  документа (п. 4.1), транзакция «файл + запись реестра» через сервисный
  слой (п. 9.2), папка контрагента с санитизацией имени и проверкой выхода
  за пределы папки документов, печатные формы записей реестра и
  `save_contract` / `save_additional` / `save_spec` — включая честную
  обработку неудачного открытия файла (п. 6.2: тост не обещает «открыт»).
  main.py: 3 775 → 3 268 строк; ContractApp: 3 310 → 2 779 строк.
* **Состояние страницы остаётся на приложении.** Виджеты и переменные
  публикуются под прежними именами (`spec_text`, `spec_table`,
  `spec_party_var`, `spec_contract_var`, `spec_number_var`…), а таймер
  отложенного предпросмотра живёт в `app._spec_preview_after` — его читают
  защита несохранённых данных (п. 4.2, 4.4), страницы договора и
  доп. соглашения и smoke-тест; контроллер владеет кодом, а не данными
  страницы. Контроллер создаётся в `__init__` ДО построения страниц:
  `_build_spec_page` уже идёт через контроллер.
* **Маршрутизация подмен smoke-теста.** Фасады с прежними именами остались
  на ContractApp: `_build_spec_page`, `_spec_rows` (property),
  `_add_spec_row`, `_remove_spec_row`, `_spec_items`, `_spec_total`,
  `_on_spec_item_changed`, `_on_spec_party_changed`, `_persist_document`,
  `_party_documents_dir`, `_render_contract_docx`, `_render_additional_docx`,
  `_render_spec_docx`, `_rec_is_ip`, `_build_record_docx`, `_write_docx`,
  `_save_and_open_document`, `_persist_document_result_alert`,
  `_regenerate_spec`, `_flush_spec_preview`, `_render_spec_preview`,
  `_confirm_document_duplicate`, `save_contract`, `save_additional`,
  `save_spec`. Открытие файла после сохранения идёт через фасад
  `ContractApp._open_file` — его тело резолвит модульный `main.open_file`
  на каждый вызов, поэтому подмена smoke-теста видна (п. 6.2).
* **Зависимости от модуля main — только поздним импортом.** Контроллер
  берёт константы разметки (`ENTRY_WIDTH`, `SHORT_WIDTH`,
  `LEFT_PANEL_WIDTH`) и печатные настройки (`get_spec_settings`, год — на
  момент вызова, аудит 2.0.1) через `import main` внутри методов: обычный
  верхнеуровневый импорт дал бы цикл, а к моменту вызова main уже
  полностью инициализирован. Остальные зависимости — модули `services`,
  `storage`, `ui_macos`, `document_builder`, `widgets` — импортируются
  напрямую, как в предыдущих контроллерах.

### Тесты
* pytest: 256 → 302 тестов. Новый `tests/test_document_save_controller.py`
  (46) без Tk: таблица позиций (фильтр, суммы Decimal, маршрутизация строк),
  договор-основание (подстановка автоматически, честная подсказка без
  договоров), отложенный предпросмотр (перенос таймера, синхронный
  дособор перед сохранением), содержимое предпросмотра (заголовок, итого
  прописью, НДС, «Цены действительны до»), папка контрагента (создание,
  выход за пределы, ошибка диска — с предупреждениями), транзакция
  сохранения (папка контрагента для `save_document`), повтор номера
  (пустой номер молча, повтор требует подтверждения с названием
  существующего документа, другой тип документа игнорируется), три
  сценария `save_*` — валидация полей, отказ от повтора, успешное
  сохранение с транзакцией на реальном DataStore (файл на диске в папке
  контрагента), неудачное открытие не отменяет сохранение (п. 6.2),
  маршрутизация печатных форм в сервисный слой и все фасады ContractApp
  делегируют контроллеру.
* Покрытие: document_save_controller — 75% при вводе (виджетная часть
  покрыта smoke-тестом), main.py — 16% → 21%.

## 2.5.0 — 2026-11-19 (декомпозиция: шаг 4)

Четвёртый шаг плана P2 из аудита 2.0.1 («по одному контроллеру за
итерацию»): код страницы «Реестр» — построение, поиск, выбор, рендер секций
и сверка с папкой документов — вынесен в RegistryController. Поведение
приложения не менялось: полный pytest 232 → 256 и smoke 306/306 зелёные.

### Архитектура
* **registry_controller.py — RegistryController (P2).** Код страницы
  «Реестр» переехал из main.py целиком: построение страницы, поиск по
  названию и ИНН с фильтрацией по мере ввода (п. 4.5), выбор контрагента с
  частичным обновлением без пересоздания строк (п. 5.1), ленивый рендер
  списка при старте (п. 9 этапа 5), секции «документы контрагента»,
  «неопознанные» и «корзина», фоновая сверка реестра с папкой документов и
  диалог разбора файлов вне реестра (п. 2.4). main.py: 4 273 → 3 775 строк;
  ContractApp: 3 808 → 3 310 строк.
* **Состояние страницы остаётся на приложении.** Виджеты и переменные
  публикуются под прежними именами (`pages`, `registry_search_var`,
  `registry_list`, `_registry_selected_id`, `_registry_rows`,
  `_registry_docs_frame`, `_registry_rendered`, `_orphans`): их читают и
  меняют другие страницы, сценарии сохранения и smoke-тест — контроллер
  владеет кодом, а не данными страницы. Контроллер создаётся в `__init__`
  ДО построения страниц: `_build_registry_page` уже идёт через контроллер.
* **Маршрутизация подмен smoke-теста.** Фасады с прежними именами остались
  для внешних вызывающих: `_build_registry_page`, `refresh_registry`,
  `_registry_apply_filter`, `_select_registry_party`,
  `_scan_documents_consistency`. Кнопки страницы вызывают фасады приложения
  (`_edit_counterparty`, `_delete_document`, `export_document`,
  `_restore_*`, `_empty_trash`…); `_choice_dialog` — через приложение
  (instance-атрибут); показ папки для неопознанных файлов — через фасад
  `ContractApp._show_in_folder`, тело которого резолвит модульный
  `main.show_in_folder` на каждый вызов.
* **Перерисовки реестра не дублируются.** Все вызовы `refresh_registry`
  из сценариев сохранения, импорта, корзины и выбора страницы попадают в
  один фасад приложения и дальше в `RegistryController.refresh()` —
  частичное обновление при выборе (п. 5.1) по-прежнему отделяется от
  полной перерисовки с журналированием медленных (п. 10 этапа 5).

### Тесты
* pytest: 232 → 256 тестов. Новый `tests/test_registry_controller.py` (24)
  без Tk: поиск (подстрока названия, цифры по ИНН, пустой запрос), текст
  строки контрагента (тип, ИНН, ID, усечение адреса, маркер выбора),
  выбор/сброс контрагента и перенос на страницы документов, ленивый рендер,
  отложенный поиск с переносом задачи (after_cancel), фоновая сверка
  (результат на приложении, тихая обработка сбоя, обновление только при
  открытой странице), диалог разбора файлов (нет файлов, «Восстановить»
  с успехом и ошибкой хранилища, «В корзину», «Оставить»), все 5 фасадов
  делегируют контроллеру.
* Покрытие: registry_controller — 38% при вводе (виджетная часть покрыта
  smoke-тестом), main.py — 15% → 16%.

## 2.4.0 — 2026-11-19 (декомпозиция: шаг 3)

Третий шаг плана P2 из аудита 2.0.1 («по одному контроллеру за итерацию»):
сценарии реестра «экспорт/открытие документа» и «корзина» вынесены в
LifecycleController. Поведение приложения не менялось: полный pytest
203 → 232 и smoke 306/306 зелёные.

### Архитектура
* **lifecycle_controller.py — LifecycleController (P2).** Жизненный цикл
  записей реестра переехал из main.py целиком: открытие/экспорт документа
  (импортированные открываются по исходному файлу, созданные в программе
  собираются из шаблона; утерянный оригинал — явный диалог «показать папку
  или пересобрать», п. 2.9), подтверждения удаления документа и контрагента
  с описанием последствий и повторное подтверждение при >20 документах
  (п. 2.5), восстановление из корзины, окончательное удаление и «Очистить
  корзину» (п. 2.6). main.py: 4 481 → 4 272 строк; ContractApp:
  ~4 017 → 3 808 строк.
* **Маршрутизация подмен smoke-теста.** Контроллер без собственной
  логики оболочки: `_choice_dialog` всегда идёт через приложение
  (instance-атрибут, как подменяет smoke-тест); `ui.confirm`/`ui.alert` —
  атрибуты общего модуля ui_macos, подмена `m.ui.confirm` видна напрямую.
  Открытие файлов и показ папки идут через новые фасады приложения
  `ContractApp._open_file` / `ContractApp._show_in_folder` — их тела
  резолвят модульные `main.open_file` / `main.show_in_folder` на каждый
  вызов, поэтому подмена `m.open_file` / `m.show_in_folder` из smoke-теста
  продолжает действовать для кода контроллера.
* **Фасады с прежними именами.** `export_document`, `_delete_document`,
  `_delete_counterparty`, `_restore_document`, `_restore_counterparty`,
  `_purge_document`, `_purge_counterparty`, `_empty_trash` остались на
  ContractApp и делегируют контроллеру — кнопки реестра, раздел «Корзина» и
  smoke-тест работают без единой правки сценариев.
* **Контроллер без состояния.** В отличие от импорта и DaData здесь нет
  потоков и очередей: каждая операция синхронна и завершается обновлением
  UI через приложение (реестр, статус, предпросмотры, комбобоксы
  контрагентов); сброс выбора реестра `_registry_selected_id` остаётся
  состоянием приложения — контроллер меняет его через `self.app`.

### Тесты
* pytest: 203 → 232 теста. Новый `tests/test_lifecycle_controller.py` (29)
  на настоящем DataStore без Tk: отмена/подтверждение удаления документа и
  контрагента (текст подтверждения — тип, номер, контрагент, судьба файла),
  двойное подтверждение при >20 документах, сброс выбора реестра только для
  удаляемой карточки, восстановление/окончательное удаление с ветками
  `store.last_error`, «Очистить корзину» без вопросов при пустой корзине,
  экспорт (папка для «неопознанных», исходный файл для импортированных,
  диалог п. 2.9: отмена/папка/пересборка с реальной записью .docx), фасады
  `_open_file`/`_show_in_folder` видят подмену модульных
  `main.open_file`/`main.show_in_folder`, все 8 фасадов делегируют
  контроллеру.
* Покрытие: lifecycle_controller — 97% при вводе, main.py — 13% → 15%.

## 2.3.0 — 2026-11-19 (декомпозиция: шаг 2)

Второй шаг плана P2 из аудита 2.0.1 («по одному контроллеру за итерацию»):
поток «Заполнить по ИНН» вынесен в DadataController, диалоговые примитивы
переехали в слой оформления. Поведение приложения не менялось: полный pytest
203/203 и smoke 306/306 зелёные.

### Архитектура
* **dadata_controller.py — DadataController (P1-2, P2).** Жизненный цикл
  запроса реквизитов по ИНН переехал из main.py: guard повторных кликов,
  busy-анимация «Загружаю реквизиты…», фоновый HTTP-воркер, опрос очереди
  результата из главного потока Tk и подстановка карточки ЕГРЮЛ/ЕГРИП
  в поля формы. Исправления аудита 2.0.1 сохранены: повторные клики при
  активном запросе игнорируются, рабочий поток не вызывает root.after().
  main.py: 4 629 → 4 481 строк; ContractApp: 4 142 → 3 992.
* **Состояние запроса принадлежит контроллеру.** ContractApp публикует
  busy через свойство `_cp_busy` с прежним именем (smoke-тест читает и
  подменяет его напрямую); `_cp_status_var` осталась на приложении — её
  использует построитель страницы контрагента. Фабрика потока передаётся
  из main на каждый вызов, как у импорта.
* **Диалоговые примитивы — в ui_macos.py (P1-2).** `ui.choice_dialog`
  (модальный диалог с N кнопками, бывший `ContractApp._choice_dialog`) и
  `ui.import_report_window` (бывшее тело `ImportController.show_report`);
  оба — чистый слой оформления: словарь подписей типов документов передаётся
  параметром, зависимость ui_macos от storage не появилась. Фасады с
  прежними именами сохранены — подмены smoke-теста продолжают работать.
* Мёртвое состояние `_cp_busy_after`/`_cp_busy_phase`/`_cp_result_queue`
  убрано из ContractApp.__init__ — теперь это внутренность контроллера.

### Тесты
* pytest: 185 → 203 теста. Новый `tests/test_dadata_controller.py` (18):
  guard повторных кликов через фасад (зеркало smoke-проверки), валидация
  ИНН по режиму карточки (10 цифр ООО / 12 ИП — регрессия дефекта 2.0.0),
  отсутствие ключа, состав воркера (ok/error через очередь), опрос результата

  с after_cancel, подстановка полей ООО/ИП (КПП в карточку ИП не попадает,
  непустой фактический адрес не затирается), проекция `_cp_busy`.
* Покрытие: dadata_controller — 94% при вводе, import_controller —
  74% (после переиспользования примитива отчёта), main.py — 12% → 13%.

## 2.2.0 — 2026-11-19 (начало декомпозиции ContractApp)

Первый шаг плана P2 из аудита 2.0.1 («по одному контроллеру за итерацию»):
оркестрация пакетного импорта вынесена из «бог-класса» ContractApp в
отдельный контроллер. Поведение приложения не менялось: полный pytest
185/185 и smoke 306/306 зелёные.

### Архитектура
* **import_controller.py — ImportController (P1-2, P2).** Жизненный цикл
  пакетного импорта переехал из main.py целиком: guard повторного входа,
  проверки пакета до запуска (количество, объём, папка документов, свободное
  место), фоновый воркер с копированием в папку контрагента, опрос очереди
  из главного потока Tk, регистрация результатов и окно отчёта.
  main.py: 5 142 → 4 629 строк; сам ContractApp: 4 655 → 4 142 строки.
* **Состояние импорта принадлежит контроллеру.** ContractApp публикует его
  свойствами с прежними именами (`_import_running`, `_import_queue`,
  `_import_win`, `_import_cancelled`) — smoke-тест, drag-and-drop-хук и
  внутренние вызовы продолжают работать через фасады с прежними именами без
  единой правки сценариев.
* **Связность контроллера минимальна.** Вызовы, которые подменяет smoke-тест
  (`_show_import_report`, `_ask_import_party`, `_choice_dialog`), всегда идут
  через фасад приложения; фабрика потока передаётся из main на каждый запуск,
  чтобы подмена `main.threading.Thread` синхронным исполнителем продолжала
  действовать; путь-хелперы настроек остаются на приложении
  (`_documents_dir_for_import`, `_is_inside_directory`).
* Канонический набор расширений импорта — `ALLOWED_EXTENSIONS` в
  import_controller (алиас `IMPORT_ALLOWED_EXTENSIONS` в main сохранён).

### Тесты
* pytest: 153 → 185 тестов. Новый `tests/test_import_controller.py` (32):
  guard re-entry через фасад (зеркало smoke-проверки), все ветки проверок
  пакета (лимит файлов, объём, недоступная папка, нехватка места), воркер
  (allowlist расширений, отмена остатка, копирование в папку контрагента),
  регистрация (attach по ИНН, create, дубликаты, «unknown», диалог привязки
  через фасад), пакетная запись одним `save()` с честным отчётом об ошибках,
  опрос очереди (status/file/done, перепланирование, остановка при закрытии).
* Покрытие: import_controller — 66% сразу при вводе (раньше логика была
  доступна только smoke), main.py — 9% → 12%.
* smoke: строковая проверка «пакет и свободное место проверяются» теперь
  смотрит и в исходник контроллера (проверка переехала вместе с кодом).

## 2.1.0 — 2026-11-19 (исправления по комплексному аудиту)

Закрыты все находки P0 и выполнимая кодом часть P1 из аудита версии 2.0.1
(54 находки: 7 P1, 18 P2, 29 P3); refactoring ContractApp (P2) — отдельно,
после стабилизации 2.1.x.

### Корректность (P0)
* **Re-entry пакетного импорта (P1-1).** Guard `_import_running` перенесён
  из диалога в `_start_documents_import`: drag-and-drop больше не запускает
  второй импорт поверх работающего (раньше это смешивало отчёт и могло
  задваивать записи). Очередь результатов у каждого запуска своя и передаётся
  воркеру через `args`. Smoke-регрессия.
* **DaData без root.after() из потока (P1-3, P2-3).** Результат запроса идёт
  через `queue.Queue` и опрашивается из главного потока (`_cp_result_tick`)
  — тот же паттерн, что у импорта. Повторные клики «Заполнить по ИНН» при
  активном запросе игнорируются (guard `_cp_busy`) — раньше два воркера
  гонялись за одними полями формы.
* **Валидаторы ячеек SpecTable включены (P2-6).** `validate="key"` для
  «Кол-во»/«Цена» (раньше Tk создавал validatecommand, но никогда его не
  вызывал); вставка из буфера (`var.set`) проходит санитизацию — буквы в
  числовые ячейки больше не попадают.
* **Ошибки сбора форм не глотаются (P1-3, P2-9).** `_cp_collect` при сбое

### Безопасность
* **Ключ DaData шифруется DPAPI (P2-1).** На Windows файл ключа пишется
  через CryptProtectData (CurrentUser), старый открытый файл мигрирует при
  первом чтении, битый контейнер не роняет программу. В настройках ключ
  больше не подставляется в поле (маска + строка статуса) — реальное
  значение не видно и не копируется. Сбой шифрования деградирует к
  открытому тексту, не теряя ключ.
* **Мьютекс: Global\ + SID (P2-2).** `Global\EWDocHub_SingleInstance_<SID>`
  защищает и от второй сессии того же пользователя (консоль + RDP), у разных
  пользователей блокировки независимы; `WinDLL(use_last_error=True)` +
  `ctypes.get_last_error()` вместо ненадёжного GetLastError; при отказе в
  доступе к Global\ — деградация на Local\ с тем же именем. Для
  инсталлятора — фиксированный `Global\EWDocHub_InstallerMutex` (AppMutex
  в installer.iss обновлён).
* **TLS-ошибки DaData видны отдельно (P3).** SSLCertVerificationError больше
  не маскируется под «нет интернета» — отдельная ветка с понятным сообщением.
* **Дисклеймер DaData** в настройках и license.txt: при автозаполнении
  отправляется только ИНН (публичный идентификатор).
