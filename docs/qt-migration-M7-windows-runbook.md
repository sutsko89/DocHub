# EW.DocHub — Windows-runbook этапа M7 (CP2): сборка, установка, замеры

Linux-часть M7 выполнена в песочнице (см. `qt-migration-M7-report.md`).
Этот runbook — приёмка на Windows (Python 3.13, Windows 10/11 x64).
Каждый шаг фиксирует результат в протокол; «не проверено» снимается
только фактом прогона, никакие критерии не засчитываются по чтению кода.

Профиль для всех прогонов — изолированный: `$env:APPDATA = "C:\bench\profile"`
(раздел И.1 плана; синтетические данные — `tools/generate_registry.py`).
Никогда не запускать на реальном профиле без чек-листа И.1 (копия BKUP-1,
кросс-тест совместимости зелёный).

## Шаг 0. Прогон тестов и smoke (гигиена перед сборкой)

```powershell
python -m pytest tests/
python smoke_test.py     # ожидание: SMOKE OK: 358 проверок
python smoke_qt.py       # ожидание: SMOKE QT OK: 145 проверок
```

Финальная строка pytest `-rs` вносится в протокол (в песочнице сводка
нестабильна — артефакт окружения; на Windows ожидается штатно).

## Шаг 1. Сборка обоих флейворов (К-3/M7)

```powershell
pyinstaller --noconfirm EWDochub.spec
pyinstaller --noconfirm EWDochub_qt.spec
```

Фиксировать:

- наличие `dist\EW.DocHub\EW.DocHub.exe` и `dist\EW.DocHub-qt\EW.DocHub-qt.exe`;
- размер папок сборки (Qt-сборка: ожидаемо +50–80 МБ к Tk — риск 1);
- старт Qt-сборки до окна и до готовности спецификации — канал
  `EWDOCHUB_PERF_LOG=1` (`startup.built/ready`) — сравнение с цифрами M2.

Если Qt-сборка не содержит exe или не стартует с ошибкой плагинов
(platforms/styles) — CI-шаг «Контрольная сборка Qt-версии» в `ci.yml`
воспроизводит то же самое; разбор по логу PyInstaller (риск 5).

## Шаг 2. Установщики (Inno Setup) — К-5

```powershell
& "C:\Program Files (x86)\Inno Setup 6\ISCC.exe" installer.iss
& "C:\Program Files (x86)\Inno Setup 6\ISCC.exe" installer_qt.iss
```

Фиксировать: `installer\EW.DocHub-2.28.2-setup.exe` и
`installer\EW.DocHub-2.28.2-qt-setup.exe`; имя Qt-ассета обязано
заканчиваться на `-qt-setup.exe` (регулярка выбора флейвора в updater
ищет именно этот суффикс).

## Шаг 3. Установка и обновление Tk 2.28.2 → Qt (критерий CP2)

1. Установить Tk-сборку 2.28.2 (`EW.DocHub-2.28.2-setup.exe`), запустить,
   создать 2–3 контрагента, договор, доп. соглашение, ключ DaData.
2. Запустить Qt-установщик поверх (`EW.DocHub-2.28.2-qt-setup.exe`):
   - мьютекс: при запущенной программе установщик предлагает закрыть
     (те же AppMutex — зафиксировать сценарий);
   - установка проходит в ту же папку ({app}), ярлыки остаются «EW.DocHub»;
   - данные: реестр, настройки (тема, сортировка реестра), ключ DaData,
     папка документов — **проверить каждый** после первого запуска Qt.
3. Первый запуск Qt-сборки: версия в «Настройках» — «2.28.2-qt»;
   база читается без миграций (schema_version = 1); журнал app.log без
   реквизитов; crash.log на месте.
4. Кросс-тест: закрыть Qt, открыть Tk 2.28.2 на том же профиле — данные
   читаются (п. 6 запрета «база после Qt-сессии читается Tk»).
5. Деинсталлятор Qt: вопрос про пользовательские данные (п. 6.5) —
   при отказе профиль остаётся.

SmartScreen/подпись: без сертификата — «неизвестный издатель» →
«Подробнее → Выполнить в любом случае» (зафиксировать текст предупреждения);
при наличии сертификата — workflow подписывает оба setup.exe (К-5 закрывается
протоколом).

## Шаг 4. SHA256SUMS и автообновление — стык с шагом 6

```powershell
Get-FileHash installer\*-setup.exe -Algorithm SHA256 | ForEach-Object {
  "$($_.Hash.ToLower())  $($_.Path.Split('\')[-1])"
}
```

Ожидание: две строки — Tk- и Qt-ассеты рядом (как соберёт release.yml).

## Шаг 5. Контрольные замеры Qt (схема раздела Е; цифры — в CHANGELOG)

Замеры на той же машине/профиле, что и «до»-цифры Tk (M0, блок E-4).
Каждый — 5 повторов, медиана; фиксируются ОС, commit, объём данных.

1. **Старт** Qt-сборки: время до окна и до готовности спецификации
   (`startup.built/ready`), WorkingSet после построения окна (К-3 база).
2. **Реестр @10k** (К-9): первое отображение, прокрутка до конца, поиск
   «5000» — сравнение с Tk 7,6 мс @1k / 413 мс @50k и M5-критерием ≤15% @10k.
3. **Вставка 500 строк** спецификации (К-10) — сравнение с Tk-замером CP1.
4. **P-08**: медиана сборки .docx на UI-потоке ≤ 50 мс (сохранение договора/
   спецификации); если медиана больше — протокол, пересмотр решения
   «P-08 не требуется» (пересмотр только по замерам, критерии те же).
5. **Память @10k** реестра — WorkingSet с открытой страницей реестра.

Все цифры внести в CHANGELOG (запись этапа M7) — критерий «замеры Qt
зафиксированы в CHANGELOG» закрывается этим шагом.

## Шаг 6. Цепочка обновления Qt→Qt (К-6; после публикации двух релизов)

Полная цепочка проверяется вручную между двумя фактическими релизами
(раздел И.2; до прогона в CP2/M8 помечается «не проверено»):

1. Релиз A содержит `EW.DocHub-<vA>-qt-setup.exe` и `SHA256SUMS.txt`
   с двумя строками; релиз B (`vB > vA`) — так же.
2. Установлена Qt-сборка vA. Автопроверка (смена `last_update_check`
   в settings.json на сутки назад) находит релиз B → диалог «Обновить
   сейчас» → скачивание **qt-ассета** (в temp\EW.DocHub-update) →
   SHA-256 по SHA256SUMS.txt → подтверждение (деструктивное) → снимок
   реестра (BKUP-1) → тихая установка /VERYSILENT → перезапуск уже vB.
3. Негативные: чужой флейвор не скачивается (проверить релиз с одним
   Tk-ассетом — диалог «установщик ещё не выложен»); SHA-256 не совпал →
   файл удалён, честное сообщение; отмена скачивания → «.part» не остаётся.
4. Tk-сборка 2.28.2 на релизе B: авто-проверка находит vB, но обновляться
   программой не должна (Tk-ассет в релизе B отсутствует — страница релиза).

## Шаг 7. К-8 — сетевая папка документов / OneDrive

Папку документов на сетевом ресурсе (или OneDrive-синхронизируемую):
сохранение договора, экспорт, сверка — фиксировать поведение и ограничения
(как в Tk-версии; отличия — протокол).

## Шаг 8. К-4 (остаток) — DPI 150% и второй монитор

Каркас Qt на 150% и перенос окна между мониторами с разным масштабом —
компоновка не ломается, клик-toggle реестра и панель действий работают.
